# 01 · 背景与目标

<a id="s1"></a>
## 一、背景

Warp 于 2026 年开源了其终端客户端（`warpdotdev/warp`）。它是一个功能完整、
工程质量很高的 GPU 终端，但**产品形态是"云端加持的终端"**：登录、遥测、崩溃
上报、云 Agent、Warp Drive 对象同步、共享会话、服务端实验开关、自动更新，
这些都编织在启动路径里，而不是可选插件。

term4u 的目标只有一句话：

> **把这个终端变成一个纯本地软件——本地终端、分栏、文件树、编辑与预览全部保留；
> 主进程不产生任何非 loopback 的出站连接，且这一点由代码结构保证，而不是由配置
> 约定保证。**

"由代码结构保证"是这个项目与"把开关关掉"的根本区别，也是全部设计复杂度的来源。

<a id="s1-1"></a>
### 1.1 为什么现成的 `warp-oss` 不够

上游已经提供了 OSS channel（`app/src/bin/oss.rs`、`crates/warp_tui/src/bin/oss.rs`），
它把遥测、崩溃上报、自动更新、MCP 静态凭据四项配成了 `None`。但它仍然写着：

```rust
server_config: WarpServerConfig::production(),   // https://app.warp.dev  wss://rtc.app.warp.dev/graphql/v2
oz_config: OzConfig::production(),               // https://oz.warp.dev
```

（`app/src/bin/oss.rs:17-18`、`crates/warp_tui/src/bin/oss.rs:19-20`）

也就是说 OSS 构建**照常初始化 Warp 生产云服务的客户端**：Firebase 认证 key
硬编码在 `crates/warp_core/src/channel/config.rs:62`，`ServerApiProvider`、
`AuthManager`、RTC WebSocket、SSE 全部照建。`warp-oss` 是"关掉了上报的云终端"，
不是"本地终端"。

<a id="s1-2"></a>
### 1.2 为什么不能只加开关

`ChannelConfig` 的 `server_config` / `oz_config` 是**非 Option 的必填字段**
（`crates/warp_core/src/channel/config.rs:16,18`）。这意味着"没有服务器"在当前
类型系统里**无法表达**。任何"填个假 URL"的做法都会引入调研原文点名的四类
故障：重试循环、后台报错、DNS 查询、未来代码误用。

因此改造的第一性动作是**让"离线"成为一个类型层面的状态**，而不是一组值。

## 三、五条硬指标

这五条来自调研原文开篇，是 term4u 的**验收定义**。凡不能被这五条之一覆盖的改动，
都不属于本项目范围。

| # | 指标 | 保证层次 | 验收方法 |
|---|---|---|---|
| **H1** | 编译时不包含遥测、Sentry、OTel、云 Agent、认证、Drive、共享、更新模块 | 编译期（feature + 物理删除） | `cargo tree` 黑名单为空 + 目标文件不存在（[07 §12](07-测试与验证策略.md#s7-12)） |
| **H2** | 启动时不创建任何 Warp Server HTTP / SSE / WebSocket 客户端 | 启动路径（`initialize_app` 三分） | 启动后 `lsof` 零外连 + 日志无云客户端构造记录 |
| **H3** | 主进程只允许 loopback，拒绝所有外部网络 | 运行期（socket 对端地址层守卫） | 守卫单测 + 系统级出站拦截下无重试 |
| **H4** | 即使以后误合并了新的云调用，也会被统一网络出口拒绝 | 运行期（同 H3，兜底） | 守卫是**默认拒绝**而非黑名单；新增调用自动被拒 |
| **H5** | 本地 Shell 子进程是否联网，由用户另行控制 | 明确的非目标 | 文档声明 + 不做任何子进程网络限制 |

**H4 是整套设计的重心。** H1/H2 是一次性的删除工作，会随上游合并而腐蚀；H3/H4 是
结构性的，只要守卫还在，腐蚀就不会变成外发。因此实施顺序上 **H3 必须排在大规模
删除之前**（见 [08 M1](08-实施顺序与里程碑.md)）。

**H5 的边界必须写进 README。** term4u 不控制你在终端里跑的 `codex` / `claude` /
`gemini` / `git` / `ssh`——它们是普通 PTY 子进程，联不联网是它们自己的事。把这条
说清楚，才不会让"本地终端"这个说法被误读成"沙箱"。

## 四、两阶段许可证终态

<a id="s4-x1"></a>
### 阶段 1（本文档主体）：AGPL + MIT 双许可 fork

保持上游的许可证结构原样：

```
term4u/                        AGPL-3.0-only（workspace 默认）
├── LICENSE-AGPL               原样保留
├── LICENSE-MIT                原样保留
├── LICENSES.md                【新增】目录级许可证地图
├── app/                       AGPL
├── crates/
│   ├── warp_core/             AGPL
│   ├── warp_terminal/         AGPL
│   ├── warpui/                MIT  ← MIT 岛
│   ├── warpui_core/           MIT  ← MIT 岛
│   ├── warpui_extras/         AGPL（注意：不在 MIT 岛内）
│   └── … 其余 76 个 crate      AGPL
└── crates-local/              【预留】自研 MIT crate 的落点，阶段 1 不创建
```

**阶段 1 不为任何一行 AGPL 代码改许可证。** 这不是保守，是唯一合法的选择：
AGPL 代码的版权属于 Denver Technologies，我们只有使用与分发的许可，没有再许可的
权利。凡是"改成 MIT"的想法，都只能通过阶段 2 的洁净室重实现达成。

### 阶段 2（[06 章](06-阶段2-完整MIT路线.md)）：完整 MIT

├── app/                       洁净室重实现 → MIT
├── crates/
│   ├── warp_terminal/         洁净室重实现 → MIT

<a id="s5"></a>
## 五、非目标（本项目明确不做）

| # | 非目标 | 理由 |
|---|---|---|
| N1 | **阶段 1 不改 `warp_*` crate 名与内部符号** | 上游合并能力是这个 fork 的生命线。改名会让每次 `git merge upstream/master` 变成成百上千的冲突。只改运行时身份与对外品牌（[05 §8](05-阶段1-仓库与品牌.md#s8)）。 |
| N2 | **不为 AGPL 代码改许可证** | 无权。见上节。 |
| N3 | **不自建云服务** | term4u 的定义就是"没有服务端"。任何"自己搭一个"的方案都会把 H2/H3/H4 重新打开。 |
| N4 | **阶段 1 不接任何 agent 协议** | `agent_protocol` / `local_agent_bridge` 是阶段 2 的内容。过渡期外部 CLI agent 只作为普通 PTY 子进程运行——这已经能用，不需要协议。 |
| N5 | **不创建自研三 crate 的空壳** | 空壳会立刻产生"依赖方向"与"许可证边界"两类规则债，而没有任何功能收益。等到真要写的时候再建。 |
| N6 | **不限制 Shell 子进程的网络** | 见 H5。这是操作系统级的事，用系统防火墙做，不在应用里做。 |
| N7 | **不做上游 PR** | term4u 的改动方向（删除云能力）与上游的产品方向相反，没有可回馈的部分。 |
| N8 | **不删 diesel 迁移** | 见 [03 §11](03-阶段1-云模块删除与离线化.md#s11) 与 [07 §9](07-测试与验证策略.md#s7-9)。删迁移会破坏旧 DB 的可加载性，而收益为零。 |
| N9 | **不重命名上游 `specs/`** | 285 个上游 spec 保留原位、只读，作为理解上游意图的资料。见 [05 §3](05-阶段1-仓库与品牌.md#s3)。 |

## 六、V0 / V1 / V2 交付节奏

节奏的划分原则是：**先拿到一个每天真的能用的本地构建，再谈干净。**

| 阶段 | 覆盖调研步骤 | 产出 | 完成标志 |
|---|---|---|---|
| **V0** | 第 1–5 步（`offline_hard` → 网络硬拒绝 → Offline Channel → 启动流程三分 → 删叶子模块） | **可日常使用的本地构建** | `term4u` 二进制能打开、分栏、跑命令、看文件树；`lsof` 零外连；presubmit 在既定豁免下通过 |
| **V1** | 第 6–8 步（删云 Server 与认证 → 处置 Agent/Drive → 清理 Cargo 依赖） | **依赖树干净的构建** | `cargo tree` 黑名单为空；`app/src/ai/blocklist` 去留决策落地 |
| **V2** | 品牌与对外发布 | **可对外发布的 term4u** | 六处运行时身份改名完成；品牌资产清空；`LICENSES.md` + NOTICES 齐备；首个 tag |

<a id="s6-x1"></a>
### 各阶段的取舍说明

**V0 刻意接受的不干净**：
- `warp_server_client` 等 crate 仍在依赖树里（只是不初始化）。
- `ServerApi` 类型仍然存在，只是变成空实现（[03 §8](03-阶段1-云模块删除与离线化.md#s8)）。
- 遥测 trait 与宏仍在（no-op shim），只删 collector 与传输（[03 §9](03-阶段1-云模块删除与离线化.md#s9)）。
- 二进制名与 AppId 仍是 `warp-*`——**这是刻意的**，见下。

**为什么改名排在最后（V2）而不是最前**：改 AppId 就是改数据目录与 keyring 命名空间
（[02 §8](02-现状审计.md#s8)）。V0/V1 期间会反复重建、反复丢弃本地数据，
此时改名毫无成本也毫无收益；一旦 M2 开始把 term4u 当日常终端用，数据目录里就有了
真实历史与真实密钥，再改名就要写迁移。所以规则是：**改名必须发生在"第一次真实
使用"之前的最后一刻，而不是之前的任何一刻。**

**V1 的唯一决策点**是 `app/src/ai/blocklist` 的去留（67 个测试文件 / 32,047 测试行 /
149 个源文件 / 98,892 源码行）。V0 按"编译保留 + ServerApi 空实现降级"处理，三条
路线在 [03 §12](03-阶段1-云模块删除与离线化.md#s12) 列表比较。

## 七、成功与失败的判据

**成功**：能在日常工作中用 term4u 替代原来的终端，且在系统级出站拦截打开的情况下
（只放行 loopback），一整天使用没有任何被拦截的连接尝试记录——**不是"请求失败"，
是"根本没有请求"**。

**失败模式（需要提前防的）**：
1. 删到一半编译不过，且不知道离能编译还有多远 → 用 [08](08-实施顺序与里程碑.md) 的里程碑切分与 [07 §3](07-测试与验证策略.md#s7-3) 的三分类防。
2. 测试从 11,498 个掉到 9,000 个，但说不清少的那些是"随模块删掉的"还是"悄悄不跑了" → 用 [07 §3](07-测试与验证策略.md#s7-3) 的测试清单 diff 防。
3. 以为删干净了，`strings` 一扫还有 `app.warp.dev` → 用 [07 §12](07-测试与验证策略.md#s7-12) 的硬验证防。
4. 上游发新版，合并冲突大到放弃 → 用 N1（不改 crate 名与符号）+ 集中式改动（choke point 优先）防。
