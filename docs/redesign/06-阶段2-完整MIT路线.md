## 一、"完整 MIT"的准确定义

<a id="s1-1"></a>
### 1.1 目标形态

```
term4u/                        MIT
├── LICENSE                    MIT（单一）
├── NOTICES.md                 第三方声明（含 Warp 的 MIT 部分）
├── crates/
│   ├── app/                   ← 洁净室重实现，MIT
│   ├── terminal/              ← 洁净室重实现（原 warp_terminal），MIT
│   ├── core/                  ← 洁净室重实现（原 warp_core），MIT
│   ├── agent_protocol/        ← 自研，MIT
│   ├── local_agent_bridge/    ← 自研，MIT
│   ├── local_fs_service/      ← 自研，MIT
│   ├── warpui/                ← Warp 原版 MIT，保留 Denver Technologies 版权声明
│   └── warpui_core/           ← Warp 原版 MIT，同上
```

<a id="s1-2"></a>
### 1.2 三个必须说清楚的点

| # | 常见误解 | 事实 |
|---|---|---|
| M1 | "完整 MIT = 整个仓库都是我们的" | **不是**。`warpui` / `warpui_core` 仍是 Warp 的作品，只是许可证是 MIT。它们的版权声明必须保留（MIT 的唯一强制要求） |
| M2 | "把 AGPL 代码改一改就能变 MIT" | **不能**。改动衍生作品仍是衍生作品，仍受 AGPL 约束。唯一合法路径是**不看 AGPL 代码，从行为规格重新实现** |
| M3 | "阶段 2 会比阶段 1 简单，因为已经删了很多" | **相反**。阶段 1 删的是云能力（约 176k 行），阶段 2 要重写的是**留下来的核心**（见 [§2](#s2)） |

<a id="s1-3"></a>
### 1.3 为什么值得做

| 动机 | 说明 |
|---|---|
| AGPL 的传染性 | 任何链接到 term4u 的作品都要 AGPL。如果将来要把终端内核做成库给别人用，AGPL 是硬门槛 |
| 分发义务 | AGPL 要求分发时提供源码。这对开源项目不是负担，但如果将来有闭源集成需求，就是 |
| 独立性 | 摆脱"我们是 Warp 的 fork"这个身份 |

> **如果这三条动机都不成立，阶段 2 就不该做。** 阶段 1 的 AGPL 形态是**完全合规、
> 完全可用**的（[04 §8](04-残余依赖与许可证架构.md#s8)），没有任何
> 法律或技术问题。阶段 2 是一个战略选择，不是修复。

## 二、重实现范围估算

<a id="s2-1"></a>
### 2.1 阶段 1 完成后剩下的代码量（当前实测，删除前）

| crate | 非测试文件 | 非测试行 | 测试文件 | 测试行 |
|---|---|---|---|---|
| `app`（含所有子模块） | 1,751 | **877,324** | 479 | 245,818 |
| `crates/warp_terminal` | 90 | 31,963 | 29 | 13,875 |
| `crates/warp_core` | 38 | 7,603 | 9 | 1,154 |
| `crates/warpui`（MIT，**不重写**） | 143 | 30,160 | 17 | 4,279 |
| `crates/warpui_core`（MIT，**不重写**） | 186 | 64,242 | 71 | 26,477 |

<a id="s2-2"></a>
### 2.2 减去阶段 1 的删除量

阶段 1 的删除集是 **408 文件 / 176,188 行**（[02 §7.7](02-现状审计.md#s7-7)），
其中绝大部分在 `app/` 里。若 `app/src/ai/blocklist` 也走
[03 §12](03-阶段1-云模块删除与离线化.md#s12) 路线 A
（整块删），再减 98,892 行。

| 情形 | 阶段 2 要重写的 `app` 非测试行（粗估） |
|---|---|
| blocklist 保留（路线 B） | 877,324 − 176,188 ≈ **701,000** |
| blocklist 删除（路线 A） | 701,000 − 98,892 ≈ **602,000** |

再加 `warp_terminal`（31,963）+ `warp_core`（7,603）。

<a id="s2-3"></a>
### 2.3 结论：**六十万行量级**

| 项 | 估算 |
|---|---|
| 需要洁净室重写的非测试行 | **60 万 – 74 万行** |
| 需要重写的测试 | 同量级（当前 `app` 测试就有 245,818 行） |
| 参照物 | 这个量级接近"从头写一个 GPU 终端 + 编辑器 + 文件树 + LSP 客户端 + 设置系统" |

> **不要用"我们已经理解了这份代码，所以重写会快"来打折。** 洁净室重实现的规则恰恰是
> **不能看原代码**（[§4](#s4)），理解得越深反而越危险。

<a id="s2-4"></a>
### 2.4 三条降低范围的路径

| # | 路径 | 能省多少 | 代价 |
|---|---|---|---|
| S1 | **大幅削减功能范围**：只做终端 + 分栏 + 文件树 + 文本预览，砍掉编辑器、LSP、code review、notebooks、workflows、settings UI 的大部分 | `app/` 里 `code/`(LSP)、`editor/`、`code_review/`、`notebooks/`、`settings_view/`（含 `features_page.rs` 7,891 行、`warp_agent_page.rs` 6,508 行）合计数十万行 | term4u 变成一个功能少得多的软件 |
| S2 | **最大化使用第三方 crate**（[§3](#s3)） | 终端模型、PTY、markdown、语法高亮、keyring 都有成熟的 MIT/Apache 实现 | 依赖增加；行为与上游会有差异 |
| S3 | **保留 `warpui` / `warpui_core` 这 94,402 行 MIT 代码** | 94,402 行（这已经是既定方案） | 依赖 Warp 的 UI 框架；`sum_tree` 等 6 个 AGPL 依赖要先解开（[§5](#s5)） |

**S1 是唯一能把量级从"六十万行"降到"可行"的路径。** 阶段 2 启动时的第一个决定
应当是**功能范围**，而不是技术方案。

## 三、第三方替代优先表

优先级规则：**MIT/Apache 优先 > 成熟度 > 与 `warpui` 的契合度**。

| 要替代的能力 | 当前实现 | 候选 | 许可证 | 备注 |
|---|---|---|---|---|
| **终端模型（VTE 解析、grid、scrollback）** | `crates/warp_terminal`（31,963 行，Alacritty 衍生） | `alacritty_terminal` | Apache-2.0 | **首选**。`warp_terminal` 本来就是它的衍生，换回原版反而更接近"不是衍生作品"的状态。加 NOTICE 即可 |
| | | `termwiz` | MIT | 次选。API 更全（含 UI 层），但与 `warpui` 的渲染模型契合度需评估 |
| **PTY** | `crates/warp_terminal/src/local_tty/`（含 Windows ConPTY，片段来自 Windows Terminal MIT） | `portable-pty`（wezterm 的） | MIT | **首选**。跨平台成熟，Windows ConPTY 已处理好 |
| **markdown 解析** | `crates/markdown_parser`（AGPL，3,401 行） | `pulldown-cmark` | MIT | 直接替换。MIT 岛只在 5 个文件 / 6 行用它 |
| **B-tree + 幺半群摘要** | `crates/sum_tree`（AGPL，1,542 行） | Zed 的 `sum_tree` | Apache-2.0 | **前提是先核验出处**（[§5.2](#s5-2)） |
| | | `crop` / `ropey` | MIT | 若只需要 rope 而不需要通用摘要树 |
| **命令补全规格** | `warp-command-signatures`（git，许可证【待核验】） | Fig autocomplete specs | MIT | 社区维护，覆盖面广。需要一个 TS→Rust 的规格加载器 |
| **keyring / 安全存储** | `crates/warpui_extras/src/secure_storage/`（AGPL） | `keyring-rs` | MIT / Apache-2.0 | 跨平台（macOS Keychain / Linux Secret Service / Windows Credential Manager）。**注意**：换实现会让已存密钥无法读取，须与改名同批做 |
| **语法高亮** | `crates/syntax_tree` + `crates/languages` | `tree-sitter` + 各语言 grammar | MIT | 上游本来就用 tree-sitter 系。直接用官方 crate |
| **错误上报宏** | `crates/warp_errors`（AGPL，458 行） | `log` + 自写 3 行宏 | MIT | 岛内只用 `report_error!`（71 次）与 `report_if_error!`（1 次） |
| **shell 家族识别** | `warp_util::path::ShellFamily`（AGPL） | 自写 enum | — | 岛内只用 2 处。3 个变体的枚举，不需要第三方 |
| **进程启动** | `crates/command`（AGPL，1,590 行） | `std::process::Command` | — | 岛内只用 4 处，全部非 macOS |
| **文本偏移量工具** | `crates/string-offset`（AGPL，232 行） | 自写 | — | **必须重写，不能复制** |

<a id="s3-1"></a>
### 3.1 一条纪律

> **凡是"整个 crate 才两百行，抄过来最省事"的，都必须重写或换第三方。**
>
> 抄 AGPL 代码进 MIT crate 是许可证违规，与代码长度无关。这条纪律在
> `string-offset`（232 行）、`warp_errors`（458 行）上尤其容易破功。

<a id="s4"></a>
## 四、洁净室纪律与衍生作品风险

<a id="s4-1"></a>
### 4.1 洁净室（clean room）的标准做法

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| **规格员**（可以读 AGPL 代码） | 阅读原实现，写出**行为规格**：输入、输出、状态机、边界条件、错误行为 | 不能把代码结构、变量名、注释、算法的具体形态写进规格 |
| **实现员**（**不能**读 AGPL 代码） | 只看规格，独立实现 | 不能查看原仓库、不能看 diff、不能问规格员"原来是怎么写的" |

<a id="s4-2"></a>
### 4.2 单人项目的现实问题

**term4u 目前是单人项目。同一个人不能既当规格员又当实现员**——这不是形式问题，
是实质问题：你已经读过原代码了，写出来的东西大概率与它同形。

| 选项 | 可行性 | 说明 |
|---|---|---|
| 找第二个人当实现员 | 理想但不现实 | 六十万行的工作量，不是找个人帮忙能解决的 |
| **拉长时间间隔** | 部分有效 | 读过原代码之后隔几个月再写，记忆会淡化。但对"我刚刚才审计过这份代码"的人无效 |
| **只重写自己确实不熟悉的部分**，熟悉的部分换第三方 | **最现实** | 这与 [§3](#s3) 的策略一致：能换第三方就换，剩下真要写的部分尽量少 |
| **接受风险并如实标注** | 诚实但有法律暴露 | 见下 |

<a id="s4-3"></a>
### 4.3 风险的诚实陈述

> **必须承认的事实**：如果重实现是由读过原 AGPL 代码的人完成的，那么"这不是衍生
> 作品"这个主张**在法律上是脆弱的**。相似的 API 形状、相同的模块划分、雷同的算法
> 选择，都可能被认为是衍生。
>
> **这个风险不能通过"我们很小心"来消除。** 能降低它的只有三件事：
>
> 1. **最大化第三方替代**（[§3](#s3)）——用别人的 MIT 代码，
>    衍生自谁一目了然；
> 2. **大幅改变功能范围与架构**（[§2.4](#s2-4) 的 S1）——
>    做的东西不一样，自然不同形；
> 3. **保留 Warp 的 MIT 部分不动**——`warpui` / `warpui_core` 本来就是 MIT，
>    不需要重写，也不需要假装不是它的。

<a id="s4-4"></a>
### 4.4 阶段 2 的启动前置条件

在写第一行阶段 2 代码之前，必须先做完这四件事：

| # | 前置 | 产出 |
|---|---|---|
| P1 | **确定功能范围** | 一份明确的"term4u 2.0 做什么、不做什么"清单。这决定了工作量是六十万行还是六万行 |
| P2 | **完成 `sum_tree` 出处核验** | [§5.2](#s5-2) |
| P3 | **完成 MIT 岛的 11 个 AGPL 依赖解耦** | [§5](#s5) |
| P4 | **咨询律师** | 洁净室的具体做法、单人项目的风险、以及"如果被认定为衍生作品"的后果，需要专业意见。本文档不能替代它 |

## 五、MIT 岛抽取工序

<a id="s5-1"></a>
### 5.1 六步

| 步 | 动作 | 验收 |
|---|---|---|
| 1 | **核验 `sum_tree` 出处** | 见 [§5.2](#s5-2) |
| 2 | **解开 11 个 AGPL 依赖**，按 [04 §6](04-残余依赖与许可证架构.md#s6) 的表逐项处理 | `script/license_boundary_allowlist.txt` 清空 |
| 3 | **删掉 3 个无用依赖** | `crates/warpui/Cargo.toml:56` 的 `sum_tree`（0 引用）、`warpui_core` 的 `command` dev-dep（0 引用）、`warpui` 的 `asset_cache` / `virtual-fs` dev-dep（抽取时不需要） |
| 4 | **`script/check_license_boundaries` 改为递归版**，无白名单 | 脚本通过 = MIT 岛的 workspace 依赖闭包里 100% 是 MIT |
| 5 | **把 `crates/warpui` / `crates/warpui_core` 复制到新仓库或新目录**，各自带一份 `LICENSE`（MIT）+ 顶层 `NOTICE` 说明来源 commit 与版权方 | `cargo build -p warpui -p warpui_core` 在新位置通过 |
| 6 | **验证独立可编译** | 在一个只含这两个 crate 的最小 workspace 里 `cargo test -p warpui -p warpui_core` 通过（88 个 `*_tests.rs`、30,756 测试行） |

<a id="s5-2"></a>
### 5.2 `sum_tree` 的出处核验必须在抽取之前

**为什么在抽取之前**：如果 `sum_tree` 是 Zed（Apache-2.0）的未标注衍生，那么
现在的 `crates/sum_tree` 就是一份**许可证声明错误**的代码（标着 AGPL，实际是
Apache-2.0 衍生）。把依赖它的 MIT 岛抽出去，会把这个问题一起带走并放大。

**核验方法**：

```bash
# 1. 取 Zed 的 sum_tree
git clone --depth 1 https://github.com/zed-industries/zed /tmp/zed
# 2. 逐文件比对 API 形状与实现
diff -u /tmp/zed/crates/sum_tree/src/tree.rs crates/sum_tree/src/lib.rs | head -200
diff -u /tmp/zed/crates/sum_tree/src/cursor.rs crates/sum_tree/src/cursor.rs | head -200
# 3. 记录结论与两侧的 commit hash
```

**三种结论与对应处置**：

| 结论 | 处置 |
|---|---|
| **确为 Zed 衍生** | ① 在 `crates/sum_tree` 加 Apache-2.0 归属头与 NOTICE；② 阶段 2 直接改用 Zed 的 `sum_tree`（Apache-2.0 与 MIT 兼容）；③ **考虑向 warpdotdev 报告这个遗漏**——这对上游也是好事 |
| **独立实现** | 阶段 2 自由处理：重写、或换 `crop`/`ropey` |
| **无法判定** | 按"可能是衍生"处置（保守）：换第三方，不重写 |

**记录落点**：`docs/redesign/baseline/sum-tree-provenance.txt`，含两侧 commit hash
与判定依据。

<a id="s5-3"></a>
### 5.3 抽取后 `warpui` / `warpui_core` 的定位

| 项 | 内容 |
|---|---|
| 许可证 | MIT（Denver Technologies 版权声明**必须保留**） |
| 维护 | term4u 自己维护，可以继续从 warpdotdev/warp 的这两个目录合并上游改动 |
| 归属声明 | 顶层 `NOTICE`：`This crate originates from Warp (github.com/warpdotdev/warp) at commit 066ec71…, MIT licensed. Copyright (C) 2020-2026 Denver Technologies, Inc.` |
| 命名 | 阶段 2 可以改名（如 `t4ui` / `t4ui_core`），但**改名不改变版权归属**——NOTICE 仍要写清来源 |

<a id="s6"></a>
## 六、自研三 crate 的设计约束

> **阶段 1 不创建这三个 crate 的骨架**（[决策 N5](01-背景与目标.md#s5)）。
> 本节只定约束，让阶段 1 的决定不堵死它们。

<a id="s6-1"></a>
### 6.1 `agent_protocol`

| 项 | 约束 |
|---|---|
| 职责 | 定义 term4u 与外部 agent runtime 之间的消息协议（会话、工具调用、审批、diff、流式输出） |
| **建议对齐 ACP**（Agent Client Protocol） | 不要发明新协议。对齐一个已有的开放协议，能立刻接上生态里已实现该协议的 agent |
| 依赖方向 | **零依赖 term4u 的任何 crate**。它是一个纯协议定义 crate（类型 + 序列化），可以独立发布到 crates.io |
| 许可证 | MIT |
| 与阶段 1 的关系 | 阶段 1 保留的 Agent UI 外壳（[03 §12](03-阶段1-云模块删除与离线化.md#s12) 路线 B）是它未来的消费方。**V1 决策时要评估：blocklist 的 `action_model` 与 ACP 的消息模型差异有多大**——差异过大则路线 B 的"UI 现成"这个理由不成立 |

<a id="s6-2"></a>
### 6.2 `local_agent_bridge`

| 项 | 约束 |
|---|---|
| 职责 | 把 `agent_protocol` 的消息桥到本地进程：spawn agent 子进程、stdio/socket 传输、生命周期管理 |
| 依赖方向 | 只能依赖 `agent_protocol` + 标准库 + 第三方。**不能依赖 `app` 或任何 UI crate** |
| **网络纪律** | 它 spawn 的 agent 子进程**可以**联网（这是 [H5](01-背景与目标.md#s3) 允许的），但 `local_agent_bridge` **自己**不能有任何网络出口。守卫（[03 §7](03-阶段1-云模块删除与离线化.md#s7)）同样适用于它 |
| 许可证 | MIT |

<a id="s6-3"></a>
### 6.3 `local_fs_service`

| 项 | 约束 |
|---|---|
| 职责 | 给 agent 提供受控的本地文件系统访问：读、写、列目录、搜索，带路径边界与审批钩子 |
| 依赖方向 | 只能依赖 `agent_protocol` + 第三方 |
| **安全纪律** | 路径边界必须是**默认拒绝**（只允许显式授权的目录），与网络守卫同构 |
| 许可证 | MIT |

<a id="s6-4"></a>
### 6.4 依赖方向铁律（入 CI）

```
agent_protocol  ←  local_agent_bridge
       ↑                  ↑
       └──  local_fs_service
                  ↑
              app / UI
```

**规则**：

1. `agent_protocol` 依赖**零个** term4u crate；
2. `local_agent_bridge` 与 `local_fs_service` 只能依赖 `agent_protocol`；
3. 三者都**不能**依赖 `app`、`warpui`、`warpui_core` 或任何 AGPL crate；
4. 反向依赖（`app` → 三者）允许。

落地：扩展 `script/check_license_boundaries`（[04 §5](04-残余依赖与许可证架构.md#s5)）
加一段依赖方向检查。**阶段 1 该段为空转**（目录不存在），但脚本框架要留好。

## 七、阶段 1 需要为阶段 2 保留的东西

这是本章对阶段 1 的**唯一硬性要求**：以下六件事在阶段 1 做，成本接近零；
不做，阶段 2 要付出很大代价补。

| # | 要保留/建立的 | 在哪一章落地 | 不做的代价 |
|---|---|---|---|
| K1 | **`script/check_license_boundaries` + 冻结清单** | [04 §5](04-残余依赖与许可证架构.md#s5) | MIT 岛的 AGPL 依赖会在阶段 1 期间悄悄增长，阶段 2 要解的结更多 |
| K2 | **`sum_tree` 出处的核验记录** | [02 §3.4](02-现状审计.md#s3-4)、[§5.2](#s5-2) | 阶段 2 抽取时才发现，会阻塞整个抽取 |
| K3 | **git 依赖许可证的核验记录（含 commit hash）** | [04 §1.1](04-残余依赖与许可证架构.md#s1-1) | 上游仓库的许可证状态会变；没有带 hash 的记录 = 没有证据 |
| K4 | **网络守卫做成独立、可复用的模块** | [03 §7.3](03-阶段1-云模块删除与离线化.md#s7-3) | 阶段 2 重写时要重新设计一遍；做成独立模块则可以直接搬（**注意它现在在 AGPL crate 里，阶段 2 要重写或从一开始就放在 `crates-local/`**） |
| K5 | **`docs/redesign/baseline/` 的测试清单** | [07 §2](07-测试与验证策略.md#s7-2) | 阶段 2 重写时无法回答"我的实现和原来行为一致吗" |

> 核心判定函数（`check_peer`，约 15 行）写成一个独立文件，并在文件头注明
> "此文件为 term4u 原创，阶段 2 将以 MIT 重新发布"**——原创代码的许可证由作者决定，
> 只要它不依赖 AGPL 代码，就可以在阶段 2 直接改成 MIT。
