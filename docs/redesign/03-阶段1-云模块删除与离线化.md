## 一、模块处置总表

处置动作的定义：

| 动作 | 含义 |
|---|---|
| **删** | 物理删除文件/目录，并从 `mod` 树摘除 |
| **空实现** | 保留类型与签名，方法体改为返回离线错误或空值（null object） |
| **shim** | 保留 trait/宏定义，实现体变为 no-op |
| **降级** | 保留 UI，接不到后端时显示明确的"本地模式不可用"，不重试、不报错 |
| **保留** | 不动 |
| **收紧** | 保留但加约束（如网络守卫） |

时机列：**V0** = 可日常使用；**V1** = 依赖树干净；**V2** = 品牌与发布；**阶段2** = 完整 MIT。

两条结构性事实（影响构建与验收，[07 §7.10.2](07-测试与验证策略.md#s7-10-2)）：

1. **`warp_tui` 依赖 `app` crate**（`crates/warp_tui/Cargo.toml:73` `warp = { workspace = true, features = [...] }`，
   未关 default features）——`cargo build -p warp_tui` 会把 `warp` 的 202 个 default feature 全部拉开。

   它的离线性由守卫（[§7](#s7)）保证，而不是由 feature 裁剪保证。
2. `crates/warp_tui/Cargo.toml:79` 有一行 **普通依赖 `warp_channel_config.workspace = true`**
   （不只是 bin 里的宏调用）——删 8 个生成器 bin 时这一行要一并删（[§3.2](#s3-2)）。

## 四、ConnectivityMode 与 Channel 变体策略

<a id="s4-1"></a>
### 4.1 类型改造

```rust
// crates/warp_core/src/channel/config.rs

/// 连通性模式。离线是一个**状态**，不是一组值 —— 这是整套设计的第一性原则。
#[derive(Debug, Deserialize, Serialize)]
pub enum ConnectivityMode {
    /// 完全离线。云配置在类型层面不存在，不可能被误读为"空字符串"或"某个地址"。
    Offline {
        /// 是否允许 loopback（本地 MCP、本地 LSP、OAuth loopback 回调需要）。
        allow_loopback: bool,
    },
    /// 连云。仅在 `#[cfg(not(feature = "offline_hard"))]` 下可构造。
    #[cfg(not(feature = "offline_hard"))]
    Cloud {
        server: WarpServerConfig,
        oz: OzConfig,
    },
}

pub struct ChannelConfig {
    pub app_id: AppId,
    pub logfile_name: Cow<'static, str>,
    pub connectivity: ConnectivityMode,          // ← 取代 server_config + oz_config
    pub telemetry_config: Option<TelemetryConfig>,
    pub autoupdate_config: Option<AutoupdateConfig>,
    pub crash_reporting_config: Option<CrashReportingConfig>,
    pub mcp_static_config: Option<McpStaticConfig>,
}
```

> **随 enum 一起 cfg 的还有**：`WarpServerConfig` / `OzConfig` 类型定义及其
> `production()` 构造器整体加 `#[cfg(not(feature = "offline_hard"))]`——否则它们在
> offline 构建里是死代码（clippy `-D warnings` 拦）且生产 URL 字符串仍进二进制
> （[07 §7.12.2](07-测试与验证策略.md#s7-12-2) 的 V2 验收过不去）。
>
> **连带的 bin 编译陷阱（必须处理）**：保留的 `warp-oss` / `warp-tui-oss` /
> 两个 `integration` bin 都手写构造 `WarpServerConfig`。`cargo nextest` / `clippy
> --all-targets` 在带 `offline_hard` 的构建里**也会编译这些 bin**（`[[bin]]` 默认
> `test = true`）→ 编译失败。处置：这四个 bin 的文件体用 cfg 双入口——
> `#[cfg(not(feature = "offline_hard"))]` 包住真 main，另给
> `#[cfg(feature = "offline_hard")] fn main() { eprintln!("not available in offline builds"); std::process::exit(2) }`。
> 约每文件 +4 行，M2 与 2.5 同批做。

**为什么用 enum 而不是 `Option<WarpServerConfig>`**（调研原文列了两种，此处选前者）：
`Option` 会让每个调用点自己决定 `None` 怎么办，而现有代码里已经有 `unwrap_or_default()`
和 `expect(...)` 的习惯（例如 `state.rs:214` 的 `.unwrap_or_default()`、`:296` 的
`.expect("Server root URL should be valid")`）。enum + `#[cfg]` 让"云配置"在
`offline_hard` 构建里**根本不存在这个类型**，误用会变成编译错误而不是运行时空串。

<a id="s4-2"></a>
### 4.2 九个访问器的改造

`ChannelState` 的九个云访问器（[02 §4.3](02-现状审计.md#s4-3)）
统一改为返回 `Result<_, OfflineError>`：

```rust
// crates/warp_core/src/channel/state.rs

#[derive(Debug, thiserror::Error)]
#[error("term4u is built offline-only; there is no {0}")]
pub struct OfflineError(&'static str);

impl ChannelState {
    pub fn server_root_url() -> Result<Cow<'static, str>, OfflineError> {
        cfg_if::cfg_if! {
            if #[cfg(feature = "test-util")] {
                Ok(Cow::Owned(MOCK_SERVER_URL.clone()))          // :276 —— 测试短路保持不变
            } else if #[cfg(feature = "offline_hard")] {
                Err(OfflineError("server root URL"))
            } else {
                Ok(CHANNEL_STATE.lock().config.connectivity.server()?.server_root_url.clone())
            }
        }
    }
    // ws_server_url / rtc_http_url / session_sharing_server_url / oz_root_url /
    // workload_audience_url / firebase_api_key / iap_config / server_root_domain 同构
}
```

**`server_root_domain()`（`:296`）必须特别处理**——它现在是
`.expect("Server root URL should be valid")`，在离线下会直接 panic。改成
`Result` 后所有调用点被编译器逼着处理。

### 4.4 Channel 变体策略：V0/V1 复用 `Channel::Oss`，不新增变体

**修正**：前一版设计"新增 `Channel::Offline` 变体、四处同步、M2 落地"。实测推翻了
"四处"——`Channel` 是被**穷尽 match** 的枚举，新增变体要同步的至少有 **11 处存活代码**

| 位置 | match 的语义 |
|---|---|
| `crates/warp_core/src/channel/mod.rs:32` | `is_dev_channel()` |
| `mod.rs:45` | `allows_server_url_overrides()` |

| `paths.rs:140` 附近 | 目录映射的第三处 match |

<a id="s5-3"></a>
### 5.3 `app_callbacks` 的四个出口

`app_callbacks()`（`:2608-2936`）注册的生命周期回调里有四个遥测出口。**修正**：前一版写
"回调本身也应删"——错。其中两个回调还承担**本地功能**，只能删回调**内部**的遥测调用：

| 回调 | 遥测出口 | 回调里的本地功能 | 处置 |
|---|---|---|---|
| `on_become_active`（`:2617`） | `ctx.record_app_focus(...)`（warpui_core 的 app focus 遥测，MIT 岛） | 无 | 回调可整删 |
| `on_resigned_active`（`:2651`） | `ctx.record_app_blur(...)`（`:2673`） | **quake mode 窗口收起 + voice_input 中断** | **保留回调，只删 `record_app_blur` 调用** |
| `on_will_terminate`（`:2678`） | `flush_telemetry_events_for_shutdown`（`:2695`） | 有（tracing shutdown 等清理） | **保留回调，删 flush 调用** —— 这是"退出时写未发送事件到本地、下次启动重发"的入口，必须删干净 |
| `on_should_close_window`（`:2739`；注意实际名字带 `_window`） | `TelemetryEvent::UserInitiatedClose` ×2、`QuitModalDisabled` | **退出确认弹窗逻辑** | **保留回调，只删遥测调用** |

> **`on_will_terminate` 是唯一会在磁盘上留下"待发遥测文件"的路径**，因此它是
> [07 §12](07-测试与验证策略.md#s7-12) 里"无待发遥测文件"这条验收的对应改动。

<a id="s5-4"></a>
### 5.4 拆分顺序（重要）

拆分是一次**纯机械的搬运**，但必须在删除之前做，理由：

1. 先拆分 → `initialize_cloud_app` 里的东西整块不编译 → 后续删除是"删已经不编译的代码"，
   风险最低；
2. 先删除 → 在 1,151 行里找哪些行该删，边删边坏，无法二分定位。

因此里程碑顺序是 **M3（三分）→ M4（删叶子）**，见 [08 章](08-实施顺序与里程碑.md)。

## 六、feature 重构

<a id="s6-1"></a>
### 6.1 三个原则

1. **`offline_hard` 是跨 crate 的**——只在 `app` 里定义没有意义，因为守卫在
   `http_client` / `websocket` 里。
2. **`local_only` 是加法定义**——从现有 202 项 `default` 做减法必然漏，而且每次
   上游加 feature 就会漏一次。
3. **`gui` 必须与 `voice_input` 解耦**。

<a id="s6-2"></a>
### 6.2 `offline_hard`

```toml
# crates/http_client/Cargo.toml
[features]
offline_hard = []

# crates/websocket/Cargo.toml
[features]
offline_hard = []

# crates/warp_core/Cargo.toml
[features]
offline_hard = ["http_client/offline_hard", "websocket/offline_hard"]

# app/Cargo.toml
[features]
offline_hard = [
    "warp_core/offline_hard",
    "http_client/offline_hard",
    "websocket/offline_hard",
]
```

> **注意 feature unification 的陷阱**：Cargo 会把同一个 crate 的 feature 在整个
> 构建图里做并集。这里是**有利的**——只要有任何一条路径开了
> `http_client/offline_hard`，守卫就生效。但反过来也意味着：**只要有任何一个
> workspace 成员在某次构建里没开它，那次构建就没有守卫。**
> 因此 [07 §10](07-测试与验证策略.md#s7-10) 的编译矩阵里，
> "默认构建仍须可编译"这一项**不带守卫**，不能用它做离线验收。

> **上游从未编译过的 feature 组合**。202 个 default 里全部非云项（粗估 100+ 个：
> `markdown_tables`、`grep_tool`、`jupyter_notebook_rendering`、`avatar_in_tab_bar`……）

> default 的逐项分类审计（M2 的产出物 `baseline/features-audit.md`：每项标
> 本地保留 / 云删除 / 待定）+ 随 M4 删除逐步收敛的过程。V0 期间 term4u 的**离线性
> 由 `offline_hard` 守卫保证，不由 feature 裁剪保证**；`local_only` 的意义是 V1 的
> 依赖树清洁与二进制瘦身。
>
> **`local_tty` / `local_fs` 的事实修正（推翻 [02 §6.5](02-现状审计.md#s6-5) 前一版的"关键陷阱"）**：
> 实测 `ai`、`lsp`、`persistence`、`repo_metadata`、`warp_core` **五个依赖 crate 各自的
> `build.rs` 也在非 wasm 目标上强制 `println!("cargo:rustc-cfg=feature=\"local_fs\"")`**
> （与 `app/build.rs:231-235` 同款）；`warp_terminal` 没有 build.rs，但它的 `local_tty`
> feature 在其源码里 **0 处使用**（`local_tty` 模块是无条件 `pub mod`，`lib.rs:6`），
> `local_fs` 也只是转发 `warp_core/local_fs`（后者自开）。
> **结论**：任何原生构建里 `persistence::MIGRATIONS`（`crates/persistence/src/lib.rs:4-6`）
> 都存在，"漏开 local_fs → 数据库不跑迁移"的风险**不成立**（RK10 相应作废）。
> 把 `local_tty`/`local_fs` 写进 `local_only` 仍然**推荐**——让语义显式、并与 wasm
> 目标的行为一致——但它不是 load-bearing。

## 七、网络硬拒绝：在 socket 对端地址层

<a id="s7-1"></a>
### 7.1 拦截层的选择不是权衡，是唯一解

| 方案 | 结果 |
|---|---|
| 在 target URI / Host 层拦截 | **误杀** `crates/websocket/src/proxy_tests.rs` 的 3 个测试（`:332-367`、`:369-402`、`:404-433`）——它们用 loopback 代理连非 loopback 的**目标 URI** |
| 在 **socket 对端地址**层拦截 | 这 3 个测试**完全不受影响**——`connect_via_proxy`（`crates/websocket/src/proxy.rs:69`）唯一的真实 socket 操作是 `TcpStream::connect((&*proxy.host, proxy.port))`（`proxy.rs:81`），即 127.0.0.1 |

详见 [02 §7.12](02-现状审计.md#s7-12)。

<a id="s7-2"></a>
### 7.2 守卫的位置

| 出口 | 文件:行 | 说明 |
|---|---|---|
| HTTP / SSE 主路径 | `crates/http_client/src/lib.rs:370-400` `execute_inner` | `self.wrapped.execute(request)` 在 `:385`(wasm) / `:391`(native) |
| **SSE 旁路** | `crates/http_client/src/lib.rs:499-~570` `eventsource` | **绕过 `execute_inner`**，`:504` / `:525` 直接调 `self.wrapped.eventsource()` —— **必须单独加守卫** |
| WebSocket 直连 | `crates/websocket/src/native.rs:49` `connect_async_with_tls_connector` | |
| WebSocket 走代理 | `crates/websocket/src/native.rs:43` → `proxy::connect_via_proxy` → `crates/websocket/src/proxy.rs:81` `TcpStream::connect` | **守卫加在 `proxy.rs:81`**，而不是 `native.rs:32` 的入口——这样代理本身是 loopback 就放行 |

<a id="s7-3"></a>
### 7.3 守卫规则

```rust
// 建议放在 crates/http_client/src/offline_guard.rs，由 websocket 也复用
// （或独立成 crates-local/offline_guard，见 06 章的自研 crate 规划）

#[derive(Debug, thiserror::Error)]
#[error("offline build refused an outbound connection to {0}")]
pub struct OutboundRefused(pub String);

/// 唯一的判定入口。规则是**默认拒绝**：只有明确在白名单里的才放行。
#[cfg(feature = "offline_hard")]
pub fn check_peer(addr: &std::net::SocketAddr) -> Result<(), OutboundRefused> {
    let ip = addr.ip();
    let allowed = ip.is_loopback()          // 127.0.0.0/8, ::1
        || ip.is_unspecified();             // 0.0.0.0 / :: —— 仅用于本地 bind
    if allowed { Ok(()) } else { Err(OutboundRefused(addr.to_string())) }
}

#[cfg(not(feature = "offline_hard"))]
pub fn check_peer(_: &std::net::SocketAddr) -> Result<(), OutboundRefused> { Ok(()) }
```

| 目标 | 判定 | 理由 |
|---|---|---|
| `127.0.0.0/8`、`::1` | **放行** | 本地 MCP、本地 LSP、OAuth loopback 回调 |
| Unix domain socket | **放行**（不经过 `check_peer`，因为它没有 `SocketAddr`） | 本地 IPC |
| 其他一切 IP | **拒绝** | H3 / H4 |
| 私有网段 `10/8`、`192.168/16`、`172.16/12` | **拒绝** | term4u 是本机软件，不是内网客户端。若将来需要，加显式配置项，**不要**默认放行 |
| 域名（未解析） | **在解析后判定**——守卫必须看到最终的 `SocketAddr` | 这正是"socket 对端地址层"的含义 |

> **`is_unspecified()` 的放行是为 bind 服务的，不是为 connect**。如果实现时能区分
> bind 与 connect，connect 路径应当去掉这一条。

<a id="s7-4"></a>
### 7.4 DNS 也要管

守卫拦在 `connect` 上时，DNS 查询**已经发生了**。而 [07 §12](07-测试与验证策略.md#s7-12)
的合格标准是"**零 DNS 查询**"。因此还需要：

| 措施 | 位置 |
|---|---|
| `reqwest` 自定义 resolver：`offline_hard` 下对非 loopback 主机名直接返回解析失败，不发查询 | `http_client::Client::new()` 构造处（`crates/http_client/src/lib.rs:138` 起的 `impl Client`） |
| `websocket` 侧同理 | `crates/websocket/src/native.rs:36` 之前 |
| 兜底：hosts 白名单只含 `localhost` | 同上 |

**这是"零 DNS"与"连接失败"的区别所在**，也是为什么验收标准不能写成"请求失败"。

<a id="s7-5"></a>
### 7.5 守卫的测试清单

| 测试 | 断言 |
|---|---|
| `guard_refuses_non_loopback_http` | `Client::get("http://198.51.100.1/")` → `OutboundRefused` |
| `guard_allows_loopback_http` | 对本地 `mockito` server 的请求正常返回 |
| `guard_refuses_non_loopback_eventsource` | `RequestBuilder::eventsource()` 走非 loopback → `OutboundRefused`（**这条最容易漏**） |
| `guard_allows_loopback_eventsource` | 本地 SSE 正常 |
| `guard_refuses_non_loopback_websocket` | `websocket::connect("wss://198.51.100.1/")` → `OutboundRefused` |
| `guard_allows_loopback_proxy_to_remote_target` | **回归测试**：loopback 代理 + 非 loopback 目标 URI **必须放行**——保护 `proxy_tests.rs:332-433` 那三个测试的语义 |

| `guard_makes_no_dns_query` | 对一个不存在的域名发请求，用本地 DNS 观测确认零查询（可用 `dtruss`/`strace` 或注入的 resolver 计数器） |

## 八、ServerApi 空实现（null object）而非删除

<a id="s8-1"></a>
### 8.1 为什么不删

调研原文建议"`offline_hard` 下不注册 `ServerApiProvider`"，并明确不建议做"指向假
地址的 ServerApi"。**本设计采纳前半句、修正后半句**：不指向假地址是对的，但
"不注册"会带来两个成本：

| 成本 | 量化 |
|---|---|
| 57 个测试文件直接调用 `ServerApiProvider::new_for_test()`（`app/src/server/server_api.rs:1409`） | 全部要改 |
| **决策 D4 要求"接不上云端的 UI 外壳先保留"** | UI 拿不到 provider 会 panic 或需要大改 |

**null object 同时解决这两件事**：类型还在、DI 还能注册、UI 拿得到、方法一律返回
明确的离线错误。

<a id="s8-2"></a>
### 8.2 空实现的形状（已实测：13 个 trait / 178 个方法）

`ServerApiProvider` 已经把能力切成了 13 个 `Arc<dyn XxxClient>`
（`app/src/server/server_api.rs:1424-1480`）——这是空实现最好的着力点：

| trait | 定义位置 | 方法数 |
|---|---|---|
| `AIClient` | `app/src/server/server_api/ai.rs:1183-1570` | **70** |
| `ObjectClient` | `crates/cloud_object_client/src/lib.rs:201-372` | 30 |
| `AuthClient` | `crates/warp_server_auth`→`crates/warp_server_client/src/auth/mod.rs:84-168` | 18 |
| `TeamClient` | `app/src/server/server_api/team.rs:72-164` | 16 |
| `HarnessSupportClient` | `app/src/server/server_api/harness_support.rs:299-371` | 13 |
| `ManagedSecretsClient` | `crates/managed_secrets/src/client.rs:50-96` | 8 |
| `IntegrationsClient` | `app/src/server/server_api/integrations.rs:57-137` | 7 |
| `WorkspaceClient` | `app/src/server/server_api/workspace.rs:46-71` | 5 |
| `BlockClient` | `app/src/server/server_api/block.rs:28-47` | 4 |
| `FactoryClient` | `app/src/server/server_api/factory.rs:33-45` | 3 |
| `ReferralsClient` | `app/src/server/server_api/referral.rs:30-36` | 2 |

**形态修正（重要）**：前一版把空实现设计成**独立类型** `OfflineServerApiProvider` 并单独注册
——行不通。实测约束：

| 约束 | 实测 |
|---|---|
| 单例按**具体类型**查找 | ~36 处 `ServerApiProvider::handle(ctx)` / `as_ref(ctx)`（含 [§9](#s9) 的遥测宏展开里写死的 `$crate::server::server_api::ServerApiProvider`）；换类型名 = 全部调用点改写 |
| `new_for_test()` 返回 `Self` | `server_api.rs:1409`，`#[cfg(any(test, all(feature = "tui", feature = "test-util")))]`——57 个测试文件依赖这个签名 |
| 13 个 getter 之外还有 `get()` | `pub fn get(&self) -> Arc<ServerApi>`（`:1418`）返回**具体类型**，约 53 处调用（多数在删除集与测试内） |

**因此：类型名 `ServerApiProvider` 一个字都不改，空实现藏在它内部**：

```rust
// app/src/server/server_api.rs —— 改造草图

pub struct ServerApiProvider {
    backend: Backend,
}

enum Backend {
    #[cfg(not(feature = "offline_hard"))]
    Cloud { server_api: Arc<ServerApi>, auth_client: Arc<dyn AuthClient> },
    Offline(Arc<OfflineApi>),          // OfflineApi 实现全部 13 个 trait
}

impl ServerApiProvider {
    #[cfg(feature = "offline_hard")]
    pub fn new_offline() -> Self { /* Backend::Offline */ }

    pub fn get_ai_client(&self) -> Arc<dyn AIClient> {
        match &self.backend { /* Cloud → server_api.clone()，Offline → offline.clone() */ }
    }
    // …13 个 getter 同构分派
}

// app/src/server/offline_api.rs（新增）
pub struct OfflineApi;

#[async_trait]
impl AIClient for OfflineApi {
    // 70 个方法。绝大多数形如：
    async fn some_call(&self, /* … */) -> Result<T> { Err(OfflineError("AI").into()) }
    // 返回集合的方法返回空集合而不是错误，避免 UI 反复重试：
    async fn list_something(&self) -> Result<Vec<T>> { Ok(Vec::new()) }
}
// …其余 12 个 trait 同构
```

**`get()` 的 ~53 处具体类型调用点**：`offline_hard` 下没有 `Arc<ServerApi>` 可给。处置：
逐处迁移到对应的 trait getter（清单化执行；其中相当一部分在删除集模块或测试
`tui_test_support.rs` / `view_tests.rs` 内，随删随修）。迁不动的（真正需要具体
`ServerApi` 的）说明该调用点本身就是云功能，进 [§1](#s1) 的删除表。

<a id="s8-3"></a>
### 8.3 三条实现纪律

1. **返回错误 vs 返回空**：查询类（list / get）返回**空集合或 `None`**，
   写入类（create / update / delete / send）返回 `Err(OfflineError)`。
   理由：查询返回错误会让 UI 显示"加载失败"并重试；返回空会让 UI 显示"没有内容"，
   这才是离线的正确语义。
2. **绝不 `todo!()` / `unimplemented!()`**——那是 panic，会在用户点到某个按钮时炸掉。
3. **绝不发请求**——即使是"看起来无害"的健康检查。空实现里不能出现 `http_client`。

<a id="s8-4"></a>
### 8.4 UI 降级要求（D4 的落地）

| UI | 降级行为 |
|---|---|
| 登录 / 账号页 | 显示"term4u 是纯本地构建，没有账号"，**不显示登录按钮** |
| Agent 视图（若保留 blocklist） | 显示"未配置本地 Agent 运行时"；输入框禁用；**不重试** |
| Warp Drive / 团队页 | 从菜单里移除（不是灰掉——灰掉的按钮还是会被点） |
| 设置页的隐私区 | 显示 [§10](#s10) 的固定值，**只读** |
| 更新检查 | 从菜单移除 |

> **"从菜单移除"优于"禁用"**：调研 §十三.3 列了一批"会打开浏览器/访问外部站点"的
> 菜单项（Privacy Policy、Data Management、Docs、GitHub Issue、Drive Web Link、
> Oz Dashboard）。这些不上传数据，但会误触。删菜单是唯一彻底的做法。

### 8.5 V1 的再评估

**前一版写"6 个宏都在 `crates/warp_core/src/telemetry.rs`、shim = 改 1 个文件"——两个数字都错。**
实测分布（调用次数为宏点计数）：

| 宏 | 定义位置 | 调用 | shim 说明 |
|---|---|---|---|
| `send_telemetry_from_ctx!` | `crates/warp_core/src/telemetry.rs:147` | 790 | 清空。现实现会查 `TelemetryContextModel` 单例——shim 后**该单例无人再查，离线入口不必注册它**（不 shim 而只清下游，`handle(ctx)` 会因未注册而 panic） |

| `record_telemetry_from_ctx!` | `crates/warpui_core/src/telemetry/mod.rs:17` | 1 | 清空（**MIT 岛**，双版权行） |

```rust
// 三个文件里的 7 个宏统一改成同一形状：
#[macro_export]
macro_rules! send_telemetry_from_ctx {
    ($event:expr, $ctx:expr) => {{
        // 故意求值参数一次，避免调用点出现 unused 警告（clippy 是 -D warnings）。
        let _ = (&$event, &$ctx);
    }};
}
```

> - **`let _ = (...)` 而不是 `{}`**：宏体直接空掉会让调用点的局部变量变成未使用，
>   而 presubmit 的 clippy 是 `-D warnings`（[02 §7.9](02-现状审计.md#s7-9)）。
> - **`let _` 求值参数 ⇒ 事件构造表达式必须仍能编译** ⇒ 这就是 [§1.1](#s1-1) 里
>   `events.rs`（7,102 行事件类型 + `enablement_state()` 实现）**必须保留**的原因。
>   其中字段类型引用了被删模块的事件变体，随对应模块删除时同步修剪变体。
> - **实现时逐个宏核对参数形态**（个别宏是 3 参：`$auth_state, $event, $executor`），
>   保证 `let _ = (...)` 语法成立。
> - 是否带 `#[cfg(feature = "offline_hard")]` 双版本：**不带**。V0 起 shim 就是唯一实现
>   （传输已删，Cloud 构建也没有可发送的去处）；这也避免宏体分叉。

## 十一、持久化：迁移不删

<a id="s11-1"></a>
### 11.1 结论

**141 个迁移、50 张表、17 张云表——一个都不删。**

<a id="s11-2"></a>
### 11.2 依据

| 论点 | 证据 |
|---|---|
| 删迁移会破坏旧 DB 的可加载性 | 迁移是有序链，删中间任何一环，`run_pending_migrations` 对已有 DB 就会失配 |
| 收益为零 | 表是惰性的：不写就没有行，不占内存、不占 CPU、不产生网络 |
| **删表声明的连带成本远超预期** | 实测：删除集**之外**仍有 **119 个文件 / 474 处**引用这 17 张云表（[02 §7.15](02-现状审计.md#s7-15)）。删声明会连带逼你删掉 `app/src/workspaces/`、`app/src/settings_view/teams_page.rs` 等一整批模块 |
| 没有迁移测试可依靠 | 全仓库**没有**迁移/schema 测试；迁移只在 `app/src/persistence/agent_tests.rs:10-11`、`block_list_tests.rs:26-27` 里作为 fixture 被间接执行 |

> **修正**：前序计划写"只删 `schema.rs` 表声明与 model 类型 → 影响 3 文件 37 处"。
> 实测存活侧 119 文件 / 474 处。**结论从"删声明"改为"连声明也不删"。**

<a id="s11-3"></a>
### 11.3 那删什么

| 删 | 不删 |
|---|---|
| 写入这些表的**云同步代码**（`SyncQueue`、`UpdateManager`、`Listener`、`CloudPreferencesSyncer`） | 表声明（`crates/persistence/src/schema.rs`） |
| 读取这些表的**云 UI**（Drive 视图、团队页——随 §1.4 删） | Rust model 类型（`crates/persistence/src/model.rs`） |
| — | 141 个迁移 |

### 13.3 收益

| 项 | 收益 |

| **仓库体积** | **−120MB**（`app/assets/windows/`），其中 77MB 是 LFS 对象——**GitHub LFS 额度直接省下来，`git lfs push` 也不必推它们** |
