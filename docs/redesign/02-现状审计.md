## 一、许可证现状

<a id="s1-1"></a>
### 1.1 三行事实

```bash
grep -n '^license' Cargo.toml                        # AGPL-3.0-only（workspace 默认）
grep -l '^license = "MIT"' crates/*/Cargo.toml app/Cargo.toml   # 只有两个
grep -rn 'SPDX-License-Identifier' app crates --include='*.rs' | wc -l   # 0
```

| 事实 | 值 | 出处 |
|---|---|---|
| workspace 默认许可证 | `AGPL-3.0-only` | `Cargo.toml:27` |
| 显式 MIT 的 crate | **仅 2 个**：`crates/warpui`、`crates/warpui_core` | `crates/warpui/Cargo.toml:7`、`crates/warpui_core/Cargo.toml:7` |
| 其余 crate | 80 个 manifest 全部 `license.workspace = true` → AGPL | 含 `app/Cargo.toml:10` |
| 版权方 | Denver Technologies, Inc.（2020–2026） | `LICENSE-AGPL:1`、`LICENSE-MIT:1` |
| **per-file 许可证头** | **全仓库 0 个 SPDX 标记，0 个项目版权头** | 见下 |
| `license-file` 键 | 全仓库 0 个 | — |

<a id="s1-2"></a>
### 1.2 `warpui_extras` 不在 MIT 岛内

这是最容易搞错的一点：`crates/warpui_extras/Cargo.toml:7` 是 `license.workspace = true`，
即 **AGPL**。它虽然叫 `warpui_*`，却是 AGPL 下游，不属于 MIT 岛。阶段 2 抽取 MIT 岛
时不能顺手带上它。

<a id="s1-3"></a>
### 1.3 仅有的 4 处第三方归属注释

全仓库只有 9 个 `Copyright` 字样命中（`.rs` 文件内），其中只有 4 处是真正的第三方归属：

| 文件:行 | 归属 |
|---|---|
| `app/src/code_review/diff_state/local.rs:4` | `Copyright (c) GitHub, Inc. See GITHUB-DESKTOP-LICENSE in this directory.` |
| `crates/warp_util/src/path/windows.rs:117` | `Adapted under the MIT License, Copyright (c) Microsoft Corporation.` |
| `crates/warp_terminal/src/local_tty/windows/pipes.rs:6` | 同上（Microsoft） |
| `crates/warp_logging/src/wasm.rs:2` | `MIT License: Copyright (c) 2018 Limira` |

其余 5 处是 UI 字符串、Info.plist 键与 Windows 资源字段，不是许可证头。

<a id="s1-4"></a>
### 1.4 `deny.toml` 的盲区（重要）

```toml
[licenses]
private = { ignore = true }        # deny.toml:17
```

`private = { ignore = true }` 的含义是：**workspace 内的 crate 从不参与许可证检查。**
后果是——如果有一天 MIT 岛里的文件引入了 AGPL crate 的代码，`cargo deny` 一声不吭。

`about.toml:24` 有同样的 `private = { ignore = true }`。

> **结论**：AGPL 渗入 MIT 岛这件事，**现有工具链没有任何一环能抓到**。这直接
> 决定了 [04 §5](04-残余依赖与许可证架构.md#s5)
> 必须新增一个自研守卫。

## 二、app→crates 分层解读

<a id="s2-1"></a>
### 2.1 规模

```bash
ls -d crates/*/ | wc -l                                             # 81
find app -name '*.rs' | wc -l                                       # 2230
find app -name '*.rs' ! -name '*_tests.rs' -print0 | xargs -0 cat | wc -l   # 877324
find crates -name '*.rs' | wc -l                                    # 1786
find crates -name '*.rs' ! -name '*_tests.rs' -print0 | xargs -0 cat | wc -l # 407041
ls app/src/ | wc -l                                                 # 129 项（62 目录 + 67 文件）
ls specs/ | wc -l                                                   # 285
ls script/ | wc -l                                                  # 42
```

| 层 | 内容 | .rs 文件 | 非测试行 |
|---|---|---|---|
| `app/` | 1 个 crate（`warp`），产品组装层 | 2,230 | 877,324 |
| `crates/` | 81 个 crate，库层 | 1,786 | 407,041 |

<a id="s2-2"></a>
### 2.2 分层含义

- **`app/` = 产品组装层。** 它是唯一的 `[package] name = "warp"`，把 81 个库
  crate 组装成产品：启动流程、DI 注册、UI 视图树、设置页、菜单。云能力的**注册点**
  几乎全在这里（`app/src/lib.rs` 3,190 行，其中 `initialize_app` 一个函数就占
  1,151 行，`:1456-2606`）。
- **`crates/` = 库层。** 单一职责、可被多个前端复用。
- **多前端复用是真实存在的**，不是理论：

  | 前端 | crate | 说明 |
  |---|---|---|
  | GUI | `app`（bin `warp-oss` 等） | 主产品 |
  | TUI | `crates/warp_tui` | **反向依赖 `app`**：`crates/warp_tui/Cargo.toml:73` `warp = { workspace = true, features = [...] }` |
  | 集成测试 | `crates/integration` | 同样反向依赖 `app`：`crates/integration/Cargo.toml:41` |
  | WASM | `crates/serve-wasm` | 不在 `default-members` |

<a id="s2-3"></a>
### 2.3 分层靠依赖边，不靠目录名

`warp_tui` 和 `integration` 这两个 `crates/` 下的 crate **反过来依赖 `app`**。
所以"`crates/` 在下、`app/` 在上"这个直觉是错的——真实的依赖图不是分层的树，
而是一个有两条回边的 DAG。

```bash
grep -rln 'warp = {\|warp\.workspace' crates/*/Cargo.toml
# crates/integration/Cargo.toml
# crates/warp_tui/Cargo.toml
```

**这条事实的三个后果**：

1. 删 `app/` 里的模块会**直接打断 `warp_tui`**——`crates/warp_tui` 有 77 个测试
   文件，其中 9 个属于类 B（见 [§7](#s7)）。
2. `--workspace` 会把 `crates/integration` 拉进来（见 [§7.3](#s7-3)）。
3. 阶段 1 的"不动目录结构"决定是对的：目录结构不是分层的载体，动它没有收益，
   却会立刻毁掉 `git merge upstream/master`。

<a id="s2-4"></a>
### 2.4 阶段策略

| 阶段 | 目录策略 | 分层保证手段 |
|---|---|---|
| 阶段 1 | **完全不动** `app/` + `crates/`；自研 MIT crate 预留 `crates-local/`（本阶段不创建） | 依赖边 + `script/check_license_boundaries` CI 规则 |
| 阶段 2 | 收敛为一层 `crates/`（`app/` 也进去） | 同上，规则更严：MIT crate 不得依赖任何非 MIT crate |

<a id="s3-4"></a>
### 3.4 `sum_tree` 出处 —— 【待核验】

```bash
grep -rniE 'zed|copyright|spdx|licen[cs]e|gpui|derived from|adapted from' crates/sum_tree
# 仅 2 处命中，均非归属：Cargo.toml:7 的 license.workspace，与 cursor.rs:569 的普通注释
```

`crates/sum_tree` 共 4 个文件（`Cargo.toml`、`src/lib.rs`、`src/cursor.rs`、
`src/lib_tests.rs`），**没有任何版权头、SPDX 标记，也没有提到 Zed 或 gpui**。

但它的 API 形状（`SumTree` / `Summary` / `Dimension` / `Cursor` / `seek`）与 Zed 的
`sum_tree` crate 高度同形。这有两种可能：

1. 独立实现了同一个经典数据结构（B-tree + 幺半群摘要），概念相同、代码无关；
2. 从 Zed（Apache-2.0）衍生而未标注归属。

**处置**：阶段 1 **不需要**处理——它是 AGPL crate 上的 AGPL 依赖，不产生新义务。
阶段 2 抽取 MIT 岛之前**必须**核验，方法与责任见
[06 §5](06-阶段2-完整MIT路线.md#s5)。在核验前，本文档不对其出处
下任何结论。

<a id="s4-2"></a>
### 4.2 `ChannelConfig` 的类型硬约束

```rust
// crates/warp_core/src/channel/config.rs:8-28
pub struct ChannelConfig {
    pub app_id: AppId,                                        // :10
    pub logfile_name: Cow<'static, str>,                      // :13
    pub server_config: WarpServerConfig,                      // :16  ← 非 Option
    pub oz_config: OzConfig,                                  // :18  ← 非 Option
```

后四项是 `Option`，前两项**不是**。这就是"离线在类型层面无法表达"的确切位置，
也是 [03 §4](03-阶段1-云模块删除与离线化.md#s4) 的改造起点。

<a id="s4-5"></a>
### 4.5 channel-config 生成器机制

`stable` / `dev` / `preview` / `local` 共 **8 个 bin**（GUI 4 + TUI 4）都写着：

```rust
ChannelState::set(ChannelState::new(Channel::Stable, warp_channel_config::load_config!("stable")));
```

`warp_channel_config` 是 workspace 内的 proc-macro crate，它调用一个**私有的、不在
仓库里的** `warp-channel-config` 二进制（由 `script/install_channel_config:14` 从
pinned rev `97a199b5bba11af9c7d3bd43dfb3669316d1f0f8` 安装）。

**关键性质：这 8 个 bin 编译得过，只在运行时 panic。** 因此它们不阻塞任何构建或
clippy，但也永远跑不起来。处置见 [03 §3](03-阶段1-云模块删除与离线化.md#s3)。

<a id="s4-6"></a>
### 4.6 `oss.rs` 就是离线模板

`app/src/bin/oss.rs` 与 `crates/warp_tui/src/bin/oss.rs` 是**唯二**手写 `ChannelConfig`
的生产入口，且已经把四项置 `None`：


**所以新增 term4u 入口不是从零写，是抄 `oss.rs` 再改两行。** 详见

### 6.5 `local_tty` / `local_fs` 不是普通 feature（关键陷阱）

三个 feature 都存在（`local_tty:795`、`local_fs:802`、`settings_file:851`），
但**前两个不是靠 Cargo 激活的**：

```rust
// app/build.rs:231-235
if target_family != "wasm" {
    println!("cargo:rustc-cfg=feature=\"local_fs\"");
    println!("cargo:rustc-cfg=feature=\"local_tty\"");
}
```

`build.rs` 直接给 **`app` 这一个 crate** 打上 `cfg`。这意味着：

- 它**不会**传播依赖侧的 feature（`ai/local_fs`、`lsp/local_fs`、`persistence/local_fs`、
  `repo_metadata/local_fs`、`warp_core/local_fs`、`warp_terminal/local_fs`、
  `warp_terminal/local_tty` 都不会被打开）；
- 把 `local_tty` / `local_fs` 写进 `local_only = [...]` 的**加法定义**里是**必要的**
  （否则依赖侧关着），但**不能指望它们是"新开的"**——`app` 自身的 cfg 早已是开的。

`settings_file`（`:851`）是普通 Cargo feature，且在 default（`:684`）内。

### 7.12 网络守卫的可测性硬约束（关键）

**必须在 socket 对端地址层拦截，不能在 target URI / Host 层。** 反例在
`crates/websocket/src/proxy_tests.rs`：

| 测试 | 行 | 代理 | 目标 URI |
|---|---|---|---|
| `connect_via_proxy_sends_correct_connect_request` | 332-367 | `127.0.0.1:{临时端口}`（:334） | `wss://target.example.com:443`（:356） |
| `connect_via_proxy_sends_auth_header` | 369-402 | `127.0.0.1:{临时端口}`（:371） | `wss://host.example.com:8443`（:389） |
| `connect_via_proxy_fails_on_407` | 404-433 | `127.0.0.1:{临时端口}`（:406） | `wss://host.example.com:443`（:425） |

`connect_via_proxy`（`crates/websocket/src/proxy.rs:69`）**唯一的真实 socket 操作**
是 `TcpStream::connect((&*proxy.host, proxy.port))`（`proxy.rs:81`）——即 loopback。
目标 host/port 只被当作字符串拼进 CONNECT 请求行（`proxy.rs:104-108`），
**没有 DNS 解析、没有对外连接**。

> **双向结论**：
> - 在 **URI 层**加守卫 → 这三个测试全部被误杀（目标 URI 是非 loopback）。
> - 在 **socket 对端地址层**加守卫 → 这三个测试**不受任何影响**（实际连的是 127.0.0.1）。
>
> 这不是"权衡"，是"只有一个答案"。

### 7.13 全仓库无真实外连测试（实测）

- `app/`、`crates/` 的 `.rs` 里没有任何针对真实主机的 `.get("https://…")` 类调用。
- 测试代码里的 `TcpStream::connect` / `TcpListener::bind` 全部是 loopback 或临时端口
  （`crates/mcp/src/oauth_tests.rs:33`、`crates/ai/src/grok_subscription/oauth_tests.rs:67,114,131,155,178,249`）。
- HTTP 测试统一走 `mockito`（`Cargo.toml:400`）。
- `http_client::Client::new_for_test()`（`crates/http_client/src/lib.rs:158-168`）
  **不加载任何 TLS 证书**并调用 `.no_proxy()`，注释直书 "we should never be making
  real requests in tests."
- 测试里出现的真实域名（`github.com`、`warp.dev`、`google.com`、`apple.com`、
  `json-schema.org`、`w3.org`）全部是惰性字符串（命令文本 fixture、plist DOCTYPE、
  schema `$schema`、SVG xmlns）。
- 87 个 `#[ignore]` 中**没有一个**是因为网络而 ignore 的。

> **推论**：加网络守卫**不会**让任何现有测试变红。这是本次改造里风险最低的一步，
> 因此排在 M1（大规模删除之前）。

>

> // crates/warpui_extras/src/secure_storage/linux.rs:106-110
> // "We can use whatever super duper foolproof secure key we want here. Here we are
> //  specifically choosing a value that will look inconspicuous in case someone chooses
> //  to scan our binary for strings."

> 1. keyring 命名空间**会随 AppId 自动改变**（因为它派生自 `data_domain()`）——

>    `releases.warp.dev`。必须写进 [07 §12](07-测试与验证策略.md#s7-12)
>    的白名单，否则会被误判为"没删干净"。（也可以顺手把这个种子换成 term4u 的字符串——
>    但那属于改动 AGPL 文件，且会让已存密钥无法解密，须与 AppId 改名同批做。）
