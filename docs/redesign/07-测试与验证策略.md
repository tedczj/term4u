# 07 · 测试与验证策略

> **本章回答一个问题：删掉 176,188 行代码之后，怎么知道剩下的东西还是对的？**
>
> "跑起来 + 抓一下网络"不是答案。那只能证明"没崩"和"这一刻没连网"，
> 不能证明"行为没漂移"，更不能区分"测试变少了"和"测试悄悄不跑了"。
>
> **本章的每一条验收标准都是一条可运行的命令或一个可观察的产物。**
> 不出现"确认无误""检查一下""应该没问题"这类不可执行表述。

## 7.1 测试实况与成本模型

<a id="s7-1-1"></a>
### 7.1.1 全量

| 指标 | 值 | 命令 |
|---|---|---|
| `*_tests.rs` 文件 | **899** | `find app crates -name '*_tests.rs' \| wc -l` |
| 这些文件的行数 | **419,112** | `find app crates -name '*_tests.rs' -print0 \| xargs -0 wc -l \| tail -1` |
| 测试函数（全仓库） | **11,498** | `grep -rhoE '^\s*#\[(tokio::)?test\]' --include='*.rs' app crates \| wc -l` |
| ↳ 在 `*_tests.rs` 之外 | 184 | 同上，`find … ! -name '*_tests.rs'` |
| `#[tokio::test]` | **169** | `grep -rhoE '#\[tokio::test\]' --include='*_tests.rs' app crates \| wc -l` |
| `#[ignore]` | **87** | `grep -rn '#\[ignore' app crates --include='*.rs' \| wc -l` |

<a id="s7-1-2"></a>
### 7.1.2 分层成本模型

| 层 | 数量 | 单次成本 | 反馈价值 | 何时跑 |
|---|---|---|---|---|
| **单元测试**（`*_tests.rs` 里的 11,314 个） | 899 文件 | 低（进程内，`App::test` 构造 UI 上下文） | 高 | **每次改动** |
| **`#[tokio::test]`（169 个）** | 分散 | 中 | **最高** —— 它们全部在**网络与进程边界**上，是离线改造最直接的回归网 | 每次改动 |
| **doc test** | — | 低 | 低 | presubmit |
| **`crates/integration` e2e（331 个）** | 2 文件生成 | **极高** —— 每个 spawn 一个真实 GUI 进程，失败自动重跑至 10 次 | 中（覆盖启动路径，但慢且 flaky） | **里程碑** |
| **`tui_integration`**（`crates/warpui_core` 的 bin 目标，`Cargo.toml:128`） | — | 中 | 中 | **不在 presubmit 里** → 手动 |
| **bench（4 个）** | `crates/editor` 2 + `crates/warp_tui` 2 | 高 | 低（性能，非正确性） | **必须过 clippy**（`--all-targets`），但不必跑 |
| **脚本测试（3 个）** | `test_factory_files_skill.py`、`test_prepare_bundled_resources`、`test_warpctrl_early_dispatch` | 低 | 低 | presubmit |

<a id="s7-1-3"></a>
### 7.1.3 `--workspace` 覆盖 `default-members` 的陷阱

```bash
# Cargo.toml:11-24 的 default-members 排除了 crates/integration 与 crates/serve-wasm
# 但 presubmit 跑的是：
cargo nextest run --no-fail-fast --workspace --exclude command-signatures-v2
#                                ^^^^^^^^^^^ 覆盖 default-members，把 integration 拉进来
```

**后果**：`cargo test` / `cargo nextest run`（不带 `--workspace`）**不跑** 331 个 e2e；
presubmit **跑**。这个差异是"本地绿了但 presubmit 红"的头号来源。

**日常快回路的正确写法**（[7.8](#s7-8)）：

```bash
cargo nextest run --workspace --exclude command-signatures-v2 --exclude integration
```

<a id="s7-1-4"></a>
### 7.1.4 bench 的 clippy 陷阱

4 个 bench 里有 3 个 `required-features = ["test-util"]`：

| bench | Cargo.toml:行 | required-features |
|---|---|---|
| `crates/editor` `buffer_bench` | `:72` | **无** |
| `crates/editor` `char_cell_bench` | `:76` | `["test-util"]` |
| `crates/warp_tui` `transcript_bench` | `:127` | `["test-util"]` |
| `crates/warp_tui` `zero_state_bench` | `:132` | `["test-util"]` |

`cargo clippy --all-targets` 会尝试构建 bench 目标。**没开 `test-util` 时，
`required-features` 会让 Cargo 跳过它们**——所以现在能过。但如果改造中动了
`test-util` 的定义，这三个 bench 会突然被拉进 clippy 范围。**这是一个隐藏的破绽**，
在 [7.10](#s7-10) 的矩阵里显式覆盖。

## 7.2 基线的建立与冻结（M0 强制前置）

> **在改动任何一行代码之前，必须有一个被记录下来的、可比对的基线。**
> 没有基线，后面所有的"测试少了 200 个"都无法判断是好是坏。

<a id="s7-2-1"></a>
### 7.2.1 环境准备

本机**未安装** pinned 工具链（`rust-toolchain.toml` 要求 Rust `1.92.0`），
且**没有 `target/`**。M0 必须包含完整的首次构建。

```bash
cd /Users/ted/workspace/term4u

# 1. 工具链（rust-toolchain.toml 会自动选 1.92.0，但要先有 rustup）
./script/install_rust
rustc --version                       # 期望：rustc 1.92.0

# 2. 平台依赖
./script/bootstrap --skip-common-skills     # ← 必须跳过，见 05 §5.2

# 3. 测试依赖（wgslfmt + cargo-nextest + cargo-binstall + build deps）
./script/install_cargo_test_deps

# 4. 首次全量构建（预期耗时数十分钟到数小时，取决于机器）
time cargo build --workspace --all-targets 2>&1 | tee docs/redesign/baseline/build-first.log
```

> **`--skip-common-skills` 是硬性的**：`script/bootstrap:11` 默认
> `INSTALL_COMMON_SKILLS=1`，会走 `script/resolve_common_skills` 从
> `raw.githubusercontent.com` **下载脚本并执行**（`:36` curl + `:44` bash）。
> 在建立"离线基线"的这一步就联网下载并执行远程代码，是自相矛盾的。

<a id="s7-2-2"></a>
### 7.2.2 首次 presubmit：**先接受现实，再改动**

```bash
./script/presubmit 2>&1 | tee docs/redesign/baseline/presubmit-first.log
```

> **修正（M0 §0.1 执行后）**：审计时记的两处"基线隐患"（`script/lint_powershell:8`
> 与 `script/install_cargo_test_deps:9` 引用不存在的文件）**都不成立**——那两个文件
> 上游都有，只是被快照剥离了（[02 §8.5](02-现状审计.md#s8-5)）。
> **`known-fail.txt` 不要预先写入它们。**

**但基线仍未必全绿**，因为 `.config/nextest.toml` 与 CI 的存在带来了新的变量：

| 变量 | 说明 |
|---|---|
| `.config/nextest.toml` `slow-timeout = 30s / terminate-after 2` | 任何超过 60s 的测试会被**杀掉**，在慢机器上是 flake 源 |
| `[profile.ci]` 的 `retries = 2`（仅 `package(integration)`） | 本地默认 profile **没有**这层重试；同一个集成测试在 CI 绿、本地红是正常的 |
| 集成测试的双层重试 | nextest `retries = 2`（最多 3 次）× harness 内部 `MAX_TEST_RUNS = 10`（`crates/integration/tests/common/mod.rs:7`） |
| 三平台矩阵 | 本地只跑一个平台，Windows/Linux 专属失败看不到 |

#### 基线必须按 **CI 的命令集**建立，不是 presubmit

CI 与 presubmit 有五处实质差异（[02 §7.9](02-现状审计.md#s7-9)）。基线若按 presubmit
建立，就与真正的门禁不是同一个东西。**冻结命令时至少要对齐这四项**：

```bash
export NEXTEST_PROFILE=ci
export RUSTFLAGS='-C debuginfo=line-tables-only --cfg=web_sys_unstable_apis'
export WARPUI_USE_REAL_DISPLAY_IN_INTEGRATION_TESTS=1
# 且所有 cargo 调用带 --locked
cargo nextest run --locked --workspace --exclude command-signatures-v2 -E "not package(integration)"
cargo nextest run --locked --workspace --exclude command-signatures-v2 -E "package(integration) and not test(shell_integration_tests)"
```

**纪律**：**首次失败的项一律记进 `known-fail.txt`，不修。** 理由是——如果一边建基线
一边修基线，就永远不知道后续的失败是"我改坏的"还是"本来就坏的"。

<a id="s7-2-3"></a>
### 7.2.3 三份基线产物

全部提交进 `docs/redesign/baseline/`：

<a id="s7-2-3-x1"></a>
#### (a) `tests.txt` —— 规范化的全量测试清单

```bash
cargo nextest list --workspace --exclude command-signatures-v2 --message-format json \
  | python3 -c "
import json,sys
d=json.load(sys.stdin)
out=[]
for bin_id, b in d.get('rust-suites', {}).items():
    for name in b.get('testcases', {}):
        out.append(f'{bin_id}::{name}')
print('\n'.join(sorted(out)))
" > docs/redesign/baseline/tests.txt
wc -l docs/redesign/baseline/tests.txt
```

> **为什么用 `nextest list` 而不是数 `#[test]`**：`grep` 数的是源码里的属性，
> `nextest list` 数的是**实际会被执行的测试**——两者的差就是被 `#[cfg]` 掉的部分。
> 只有后者能作为门禁。
>
> **`--message-format json` 的具体 schema 随 nextest 版本变化**；若上面的
> python 片段与实际输出不符，改用 `cargo nextest list --workspace ... 2>/dev/null | sort`
> 的纯文本形式（人可读、可 diff，只是格式没那么稳）。**关键是"每次用同一条命令"**，
> 而不是用哪条命令。

<a id="s7-2-3-x2"></a>
#### (b) `known-fail.txt` —— 首次即失败/flake 的项

```bash
cargo nextest run --no-fail-fast --workspace --exclude command-signatures-v2 \
  2>&1 | tee docs/redesign/baseline/nextest-first.log
grep -E '^\s+FAIL|^\s+TRY .* FAIL|^\s+SIGSEGV' docs/redesign/baseline/nextest-first.log \
  | sort -u > docs/redesign/baseline/known-fail.txt
```

**跑三遍**，把三遍结果取并集——只在某几遍失败的就是 flake，也要记进去（标注 `[flaky]`）。

<a id="s7-2-3-x3"></a>
#### (c) `ignored.txt` —— 87 个 `#[ignore]` 及其理由

```bash
grep -rn '#\[ignore' app crates --include='*.rs' \
  | sed 's/:\s*#\[ignore/\t#[ignore/' \
  > docs/redesign/baseline/ignored.txt
wc -l docs/redesign/baseline/ignored.txt      # 期望 87
```

已知构成（[02 §7.4](02-现状审计.md#s7-4)）：`crates/integration` 62 个
（其中 41 个 `"Affected by agent_view feature flag UI changes"`、10 个裸 `#[ignore]`、
6 个 `"Flaking on CI - KC looking into 3/31/26"`、4 个 `"Flakes in CI"`、1 个需真实显示器），
其余 25 个分散在各 crate。

<a id="s7-2-4"></a>
### 7.2.4 冻结记录

`docs/redesign/baseline/environment.txt`：

```bash
{
  echo "date=$(date -u +%Y-%m-%dT%H:%M:%SZ)"
  echo "commit=$(git rev-parse HEAD)"
  echo "rustc=$(rustc --version)"
  echo "cargo=$(cargo --version)"
  echo "nextest=$(cargo nextest --version)"
  echo "platform=$(uname -srm)"
  echo "cmd_list=cargo nextest list --workspace --exclude command-signatures-v2"
  echo "cmd_run=cargo nextest run --no-fail-fast --workspace --exclude command-signatures-v2"
} > docs/redesign/baseline/environment.txt
```

> **冻结的是命令，不是数字。** 后续每个里程碑都用**同一条命令**重跑并 diff。
> 换命令就等于换基线，必须重新冻结并在 `environment.txt` 里记明原因。

<a id="s7-3"></a>
## 7.3 删除类改动的测试三分类

这是本章的核心。删代码对测试的破坏**不是一种**，是三种，每种的处理方式完全不同。

<a id="s7-3-1"></a>
### 7.3.1 类 A：随模块消亡（免费，但必须登记）

| 项 | 值 |
|---|---|
| 定义 | 位于删除集内的 `*_tests.rs` |
| 实测 | **143 个文件 / 63,886 行**（占测试文件 15.9%、测试行 15.2%） |
| 处理 | 随模块一起删。**零工作量** |
| **风险** | 测试总数会掉 —— 如果不登记，就无法区分"这 143 个是计划内删的"和"另外某些悄悄不跑了" |

**必须产出 `deleted-tests.txt`**：

```bash
# script/test_inventory --deleted   （见 7.3.4）
# 内容：每个被删测试文件的路径 + 它贡献的测试函数数量 + 删除它的里程碑
```

<a id="s7-3-2"></a>
### 7.3.2 类 B：存活但编译断裂（真正的工作量）

| 项 | 值 |
|---|---|
| 定义 | 删除集之外、但引用了删除集符号的 `*_tests.rs` |
| 实测 | **151 个文件 / 146,101 行** |
| **Rust 的结构性优势** | **全部是编译错误，不会静默跳过。** 这与动态语言的"import 失败 → 整个测试文件被跳过 → CI 依然绿"截然不同 |
| 处理 | 按 choke point 批量修（[7.4](#s7-4)） |

**热点分布**：

| 目录 | 类 B 文件数 | 占比 |
|---|---|---|
| `app/src/ai/blocklist` | **43** | 28% |
| `crates/warp_tui/src` | 9 | 6% |
| `app/src/terminal/view` | 7 | |
| `app/src/terminal` | 5 | |
| `app/src/ai` | 4 | |
| `app/src/server/server_api` | 4 | |
| `app/src/settings_view` | 4 | |
| 其余 75 个目录 | 75 | |

> **`crates/warp_tui` 的 9 个是最容易被忽略的**——它是 `crates/` 下的 crate，
> 却**反向依赖 `app`**（[02 §2.3](02-现状审计.md#s2-3)）。
> 删 `app/` 的模块会直接打断它。

<a id="s7-3-3"></a>
### 7.3.3 类 C：行为漂移（最危险）

| 项 | 值 |
|---|---|
| 定义 | 编译通过、但断言的语义已经变了 |
| 候选规模 | **605 个存活测试文件**（756 − 151） |
| 为什么危险 | 它**不会红**。测试照跑照过，但它验证的东西已经不是你以为的东西了 |

**典型场景**：

| 场景 | 具体 |
|---|---|
| 初始化路径变化 | `initialize_app_for_terminal_view` 不再注册 `ServerApiProvider` → 某个测试原本走"有 provider"分支，现在走"无 provider"分支，断言恰好都成立 |
| 单例缺席导致的默认值 | 某个 `get_singleton::<T>()` 从 `Some` 变 `None`，调用方 `unwrap_or_default()` → 断言的值恰好等于 default |
| feature 变化导致的分支切换 | `#[cfg(feature = "agent_mode")]` 的分支不再编译，测试走到了 else 分支 |

**兜底手段：基线 diff + 白名单之外必须解释**

> **门禁 = 测试清单 diff，而不是"跑一次绿"。**

规则：

```
每个里程碑结束时：
  new_tests.txt vs baseline/tests.txt 做 diff
  ├─ 消失的测试 ∈ deleted-tests.txt（类 A 白名单）  → 通过
  ├─ 消失的测试 ∉ 白名单                            → 阻断，必须逐条解释
  ├─ 新增的测试（守卫测试等）                        → 记入 added-tests.txt
  └─ 数量不变但内容变了（重命名）                     → 阻断，必须逐条解释
```

**类 C 无法被 diff 抓到**（测试还在、还绿）。对付它只有两个办法：

| 办法 | 说明 |
|---|---|
| **手工场景对照**（[7.11](#s7-11)） | 删除前后各走一遍同样的 13 个场景，比对行为。这是唯一能抓到"编译过、测试绿、但用起来不对"的手段 |
| **对三个 choke point 的改动做 code review 而非只看测试** | 类 C 几乎全部源自 choke point 的语义变化。盯住那 3 个文件，比盯 605 个测试文件有效得多 |

<a id="s7-3-4"></a>
### 7.3.4 `script/test_inventory`（新增）

```bash
#!/usr/bin/env bash
# script/test_inventory —— 测试清单的产生与 diff
#
# 用法：
#   ./script/test_inventory list                # 产生当前清单到 stdout
#   ./script/test_inventory snapshot NAME       # 存一份到 docs/redesign/baseline/NAME.txt
#   ./script/test_inventory diff A B            # 比对两份快照 A.txt / B.txt
#   ./script/test_inventory classify            # 产生 类A/类B/类C 分类（见下）
set -euo pipefail
cd "$(dirname "$0")/.."

BASE=docs/redesign/baseline
LIST_CMD=(cargo nextest list --workspace --exclude command-signatures-v2)

case "${1:-}" in
  list)
    "${LIST_CMD[@]}" 2>/dev/null | sed 's/[[:space:]]*$//' | sort
    ;;
  snapshot)
    "$0" list > "$BASE/${2:?need a name}.txt"
    wc -l "$BASE/${2}.txt"
    ;;
  diff)
    diff -u "$BASE/${2:?}.txt" "$BASE/${3:?}.txt" || true
    echo "--- 消失的测试（必须全部在 deleted-tests.txt 里）---"
    comm -23 <(sort "$BASE/${2}.txt") <(sort "$BASE/${3}.txt") \
      | grep -v -f "$BASE/deleted-tests.txt" && exit 1 || echo "OK: 无白名单外的消失"
    ;;
  classify)
    python3 script/lib/classify_tests.py       # 见 02 §7.7 的分类逻辑
    ;;
  *) echo "usage: $0 {list|snapshot|diff|classify}"; exit 2 ;;
esac
```

配套的 `script/lib/classify_tests.py` 实现 [02 §7.7](02-现状审计.md#s7-7)
的分类逻辑，输入是 `script/deletion_set.txt`（删除集清单，与
[03 §1](03-阶段1-云模块删除与离线化.md#s1) 的总表一一对应），
输出四份文件：`class-a.txt`、`class-b.txt`、`class-c-candidates.txt`、`deleted-tests.txt`。

> **它已经写好了**：见 [`tools/classify_tests.py`](tools/classify_tests.py) 与
> [`tools/deletion-set.txt`](tools/deletion-set.txt)——[02 §7.7](02-现状审计.md#s7-7) 与本节的
> 每个分类数字都由它产出，现在就能跑：`python3 docs/redesign/tools/classify_tests.py`。
> M0 时 `cp docs/redesign/tools/deletion-set.txt script/deletion_set.txt` 即可接入。

**`script/deletion_set.txt` 必须是可执行的真相**——删除动作本身也应该从它派生：

```bash
# 删除的执行方式（而不是手工 rm）
while read -r p; do [ -n "$p" ] && git rm -r --quiet "$p"; done < script/deletion_set.txt
```

这样"计划删什么"和"实际删了什么"永远一致。

<a id="s7-4"></a>
## 7.4 三个 choke point 与修复顺序

<a id="s7-4-1"></a>
### 7.4.1 修复顺序

顺序不是随意的：**每一步都让下一步的工作量变小。**

| 序 | choke point | 位置 | 改什么 | 解锁什么 |
|---|---|---|---|---|

<a id="s7-7"></a>
## 7.7 clippy 是最响的门

<a id="s7-7-1"></a>
### 7.7.1 为什么

presubmit 跑三遍 clippy，全部 `-D warnings --all-targets --tests`：

```
cargo clippy --workspace --exclude warp_completer --all-targets --tests -- -D warnings
cargo clippy -p warp --all-targets --tests -- -D warnings
cargo clippy -p warp_completer --all-targets --tests -- -D warnings
```

大规模删除必然产生两类洪水：

| 类 | 来源 |
|---|---|
| `unused_imports` / `unused_variables` | 删了被引用的东西，`use` 还在 |
| **`dead_code`** | **模块从 `pub` 转私有会暴露此前不可见的死代码**。一个 `pub fn` 只要还 `pub`，clippy 就不会说它死；一旦它所在的模块不再 `pub`，整条调用链上的死代码全部现形 |

第二类是**惊喜的主要来源**——它的量无法事先估计，只能在做的时候发现。

<a id="s7-7-2"></a>
### 7.7.2 三条纪律

| # | 纪律 | 理由 |
|---|---|---|
| D1 | **每个里程碑内，先把 clippy 收敛到零，再跑测试** | clippy 红的时候，`cargo nextest` 可能根本编译不过；先修 clippy 能让测试反馈变得可信 |
| D2 | **禁止用 `#[allow(dead_code)]` 掩盖** | `dead_code` 警告正是在告诉你"这段代码没人调用了"——那往往意味着**它也该删**。`allow` 会把漏删藏起来，让删除工作永远做不完 |
| D3 | 允许的例外：**为 shim 保留的宏参数** | [03 §9.2](03-阶段1-云模块删除与离线化.md#s9-2) 的 `let _ = (...)` 技巧就是为此。用 `let _ =` 而不是 `#[allow(unused)]` |

<a id="s7-7-3"></a>
### 7.7.3 dead_code 的正确用法：当删除清单用

```bash
# 每个里程碑结束时跑一次，把 dead_code 警告转成下一批删除候选
MILESTONE=m4        # 当前里程碑
cargo clippy --workspace --all-targets --tests --message-format short 2>&1 \
  | rg 'never used|never read|never constructed' \
  | sort -u > "docs/redesign/baseline/dead-code-${MILESTONE}.txt"
wc -l "docs/redesign/baseline/dead-code-${MILESTONE}.txt"
```

> **这份文件的行数应当在每个里程碑之后先涨后跌**：删模块 → 死代码暴露（涨）→
> 删死代码（跌）。如果它只涨不跌，说明在用 `allow` 掩盖。

```bash
TERM4U_DATA_DIR=/tmp/term4u-dbtest ./target/debug/term4u &
PID=$!
sleep 15
# 1. 进程还活着（没因为 schema 不匹配而 panic）
kill -0 $PID && echo "DB1 OK: process alive" || echo "DB1 FAIL"
# 2. 没有迁移错误
grep -i 'migration\|schema' /tmp/term4u-dbtest/logs/term4u.log | grep -i 'error\|fail' \
  && echo "DB2 FAIL" || echo "DB2 OK"
# 3. 历史条数与改造前一致
DB=$(find /tmp/term4u-dbtest -name '*.sqlite' | head -1)
sqlite3 "$DB" 'select count(*) from history;'        # 与基线记录比对
kill $PID
```

> **`MIGRATIONS` gated on `local_fs`**（`crates/persistence/src/lib.rs:4-6`）——
> 如果 `local_only` feature 集里漏了 `persistence/local_fs`
> （[03 §6.3](03-阶段1-云模块删除与离线化.md#s6-3)），**数据库根本不会跑迁移**，
> 而症状会是"某张表不存在"这种看起来毫不相干的错误。DB2 这条验收就是为了抓它。

<a id="s7-9-3"></a>
### 7.9.3 没有迁移测试可依靠

全仓库**没有**专门的迁移或 schema 测试。迁移只在两处作为 fixture 被间接执行：

| 文件:行 | 内容 |
|---|---|
| `app/src/persistence/agent_tests.rs:2,10-11` | `conn.run_pending_migrations(::persistence::MIGRATIONS)` |
| `app/src/persistence/block_list_tests.rs:11,26-27` | 同上 |

> **修正（M0 §0.1 执行后）**：Rust 侧确实没有迁移测试，但 **CI 有一道 schema 门禁**——
> `.github/workflows/ci.yml:535-560` 的 `database-migration` job：把 141 个迁移跑到
> 一个空 sqlite，再 `diff -u old-schema.rs <(diesel print-schema ...)`。
> 仅当 `crates/persistence/src/schema.rs` 或 `migrations/**` 变动时触发。
>
> **这道门禁强化了 [03 §11](03-阶段1-云模块删除与离线化.md#s11) 的结论**：
> 从 `schema.rs` 删掉一张表声明、却不删对应迁移，会**直接把这个 job 打红**。
> 而删迁移又会破坏旧 DB 可加载性。两头堵死 → **迁移与表声明都不动**是唯一自洽的选择。
>
> 所以保护有两层：CI 的 `database-migration` job（结构一致性）+ 7.9.2 的手工验收
> （旧 DB 可加载性）。前者 term4u 的 CI 要保留（[05 §2.2](05-阶段1-仓库与品牌.md#s2-2)）。

<a id="s7-10-2"></a>
### 7.10.2 feature unification 的陷阱（必须理解）

Cargo 把同一个 crate 的 feature 在整个构建图里取并集。这意味着：

| 情形 | 后果 |
|---|---|
| F1（`--features local_only`）→ `http_client/offline_hard` 开 | 守卫生效 ✅ |
| F4（`cargo build --workspace`）→ 没有任何成员开 `offline_hard` | **守卫不生效** ⚠️ |
| `cargo clippy --workspace`（presubmit 第 3 步）拉进 `warp_tui`，而它 `warp = { workspace = true, features = [...] }` | `warp` 的 feature 集是并集，**可能意外打开某些 default feature** |

> **实践规则**：**离线相关的验收只在 F1/F3 的产物上做**。F4/F5 只验证"编译得过"，
> 不验证"是离线的"。把这两件事混起来是最容易出的错。

### 7.12.5 V5：系统级出站拦截（第二道防线）

配置系统防火墙，只对 term4u 主进程放行 loopback：

| 平台 | 工具 |
|---|---|
| macOS | Little Snitch / LuLu / `pf`。规则：`term4u` 主进程 → 只允许 `127.0.0.1`、`::1`，其余全部拒绝并**记录** |
| Linux | `nftables` + cgroup 匹配，或 `firejail --net=none` 加白名单 |

**关键在"记录"而不是"拒绝"** —— 如果守卫工作正常，防火墙的拒绝日志应当是**空的**。
一旦出现条目，说明守卫漏了一条路径。

> **子进程要单独放行**：Shell、`git`、`ssh`、外部 CLI agent 是独立进程，
> 按 [H5](01-背景与目标.md#s3) 由用户自行决定。防火墙规则要按进程而不是
> 按进程树设置。

### 7.13.2 什么情况下允许里程碑"带红通过"

只有一种：**红的项在 `known-fail.txt` 里，且它在 M0 就是红的。**

任何新出现的红，都必须在里程碑关闭前变绿或写进 `known-fail.txt` 并附**书面理由**
