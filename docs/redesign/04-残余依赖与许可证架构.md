<a id="s1-2"></a>
### 1.2 无许可证声明意味着什么

如果核验结果确认某个依赖**没有许可证文件**：

| 情形 | 后果 |
|---|---|
| 它随模块删掉了（`session-sharing-protocol`、`warp_multi_agent_api`） | **问题自动消失**，无需处理 |
| 它要保留（假设 `command-corrections` 真的无许可证） | **不能再分发**。选项：① 向上游申请补 LICENSE；② 替换为等价的 OSS 实现；③ 只在本地构建使用、不发布二进制（AGPL 仓库公开源码不受影响，因为源码不含它，只含一个 git URL） |

> **③ 是 term4u 的默认姿态**：仓库里只有 `Cargo.toml` 中的 git URL 和 rev，
> 不 vendored 其代码，所以**公开仓库不构成对它的再分发**。只有当发布预编译二进制时
> 才需要解决。这把问题从 V0 推迟到了 V2。

<a id="s2-2"></a>
### 2.2 三条依赖策略

| # | 策略 | 理由 |
|---|---|---|
| P1 | **所有 git 依赖必须 rev pin，不得 branch pin** | `email_address` 的 `branch = "main"` 会让构建不可复现，且上游一改就悄悄变。改法见下 |
| P2 | **只要 term4u 不 vendored 这些 fork 的源码，就不构成再分发** | 仓库里只有 URL + rev。义务在"发布二进制"时才产生（[§7](#s7)） |
| P3 | **一旦某个 fork 的上游发布了包含 Warp 补丁的版本，就切回 crates.io** | 减少对 warpdotdev 组织的长期依赖。这是 V2 之后的持续维护项，不阻塞任何里程碑 |

P1 的落地：

```toml
# app/Cargo.toml:102 —— 现状
email_address = { git = "https://github.com/warpdotdev/rust-email_address", branch = "main" }

# 改为（rev 取自 Cargo.lock 中该包的实际 commit）
email_address = { git = "https://github.com/warpdotdev/rust-email_address", rev = "<从 Cargo.lock 读出>" }
```

```bash
# 取 rev：
rg -A2 'name = "email_address"' Cargo.lock | rg 'source = "git\+'
```

<a id="s4-1"></a>
### 4.1 为什么阶段 1 不加 per-file SPDX 头

| 论点 | 说明 |
|---|---|
| 上游零 per-file 头 | 全仓库 **0 个** `SPDX-License-Identifier`（[02 §1.1](02-现状审计.md#s1-1)） |
| 加头 = 触碰 4,016 个文件 | `app/` 2,230 + `crates/` 1,786。每次 `git merge upstream/master` 都会在这 4,016 个文件的第 1 行制造冲突 |
| 收益低 | 许可证边界已经由 manifest 的 `license` 字段 + `LICENSES.md` + CI 守卫三重表达 |
| 阶段 2 再加 | 那时不再合并上游，加头没有成本 |

<a id="s4-2"></a>
### 4.2 修改 MIT 岛文件时的双版权行

MIT 岛内**确实会被改动**——[03 §1.1](03-阶段1-云模块删除与离线化.md#s1-1) 要求把
`crates/warpui_core/src/telemetry/`、`app_focus_telemetry.rs` 改成 shim。这些是 MIT 文件。

MIT 许可证要求"The above copyright notice ... shall be included in all copies or
substantial portions of the Software"。**上游这些文件没有 per-file 版权头**，
声明在 `LICENSE-MIT` 里。因此：

- **不需要**为了改动而加原作者的版权头（它已经在 `LICENSE-MIT` 里）；
- **应当**在被实质改动的 MIT 文件顶部加一行修改说明，形式如：

```rust
// Modified for term4u: telemetry transport removed; this module is a no-op shim.
// Original: Copyright (C) 2020-2026 Denver Technologies, Inc. (MIT, see /LICENSE-MIT)
```

> **这不是 MIT 的强制要求，是好习惯**——它让下一个读代码的人立刻知道"这文件和上游
> 不一样了"。**AGPL §5(a) 对 AGPL 文件则是强制要求**（"carry prominent notices
> stating that you modified it, and giving a relevant date"），但那条可以由 git
> 历史 + README 的 fork 声明在**作品层面**满足，不必逐文件加。见 [§8.2](#s8-2)。

## 五、CI 守卫 `script/check_license_boundaries`

<a id="s5-1"></a>
### 5.1 为什么必须自研

`cargo deny` 和 `cargo about` 都设了 `private = { ignore = true }`
（`deny.toml:17`、`about.toml:24`），**workspace 内的 crate 从不参与许可证检查**。
所以"AGPL 渗入 MIT 岛"这件事，现有工具链一环都抓不到。

<a id="s5-2"></a>
### 5.2 守卫规则

```bash
#!/bin/bash
# script/check_license_boundaries
#
# 规则：MIT crate 只能依赖 MIT crate（workspace 内）。
# 阶段 1 的现实是 MIT 岛有 11 个 AGPL 依赖（见 04 章 §6），所以本脚本
# 以"白名单 + 不得增长"的形式运行：已知的违规记录在 ALLOWED 里，
# 新增任何一条都会失败。
set -euo pipefail
cd "$(dirname "$0")/.."

MIT_CRATES="warpui warpui_core"

# 已知的既有违规（阶段 1 冻结清单）。阶段 2 逐条清零，届时本文件应为空。
ALLOWED_FILE="script/license_boundary_allowlist.txt"

fail=0
for c in $MIT_CRATES; do
  # 列出该 crate 的 workspace-local 依赖（path 依赖）
  deps=$(cargo metadata --no-deps --format-version 1 \
    | python3 -c "
import json,sys
m=json.load(sys.stdin)
name=sys.argv[1]
for p in m['packages']:
    if p['name']==name:
        for d in p['dependencies']:
            if d.get('path'):
                print(d['name'])
" "$c")
  for d in $deps; do
    lic=$(cargo metadata --no-deps --format-version 1 \
      | python3 -c "
import json,sys
m=json.load(sys.stdin)
for p in m['packages']:
    if p['name']==sys.argv[1]:
        print(p.get('license') or '')
" "$d")
    if [ "$lic" != "MIT" ]; then
      if grep -qx "$c -> $d" "$ALLOWED_FILE" 2>/dev/null; then
        continue
      fi
      echo "LICENSE BOUNDARY VIOLATION: MIT crate '$c' depends on non-MIT crate '$d' ($lic)"
      fail=1
    fi
  done
done

# 反向规则：crates-local/ 下的自研 MIT crate 不得依赖任何 AGPL crate（无白名单）
# （阶段 1 该目录不存在，本段为空转）

exit $fail
```

冻结清单 `script/license_boundary_allowlist.txt` 的初始内容（来自
[02 §3.2](02-现状审计.md#s3-2)）：

```
warpui -> warp_errors
warpui -> markdown_parser
warpui -> sum_tree
warpui -> command
warpui -> asset_cache
warpui -> virtual-fs
warpui_core -> warp_errors
warpui_core -> warp_util
warpui_core -> markdown_parser
warpui_core -> string-offset
warpui_core -> sum_tree
warpui_core -> settings_value
warpui_core -> command
```

（`settings_value_derive` 与 `websocket` 是二级，脚本只查直接依赖；阶段 2 的抽取
工序会用递归版本，见 [06 §5](06-阶段2-完整MIT路线.md#s5)。）

## 八、AGPL 合规边界

<a id="s8-1"></a>
### 8.1 什么时候有义务

| 情形 | AGPL 义务 |
|---|---|
| 本地自用，不分发 | **零义务**。AGPL 只在"conveying"（分发）与"remote network interaction"（§13）时触发 |
| `tedczj/term4u` 设为**私有** | 零义务（没有分发给第三方） |
| `tedczj/term4u` 设为**公开** | 公开仓库**本身即满足**"分发时提供 Corresponding Source" |
| 发布预编译二进制 | 必须提供对应源码。若二进制来自某个 tag，则**该 tag 是公开的**就已满足 |
| **§13 远程网络交互** | term4u 的整个设计目标就是"没有网络交互"。**§13 天然不适用**——它要求"if your version supports such interaction"，而 term4u 明确不支持 |

> **结论：无论 `tedczj/term4u` 公开还是私有，都合规。** 唯一的红线是
> **AGPL 部分不得转为专有**（不能声称 `app/`、`crates/warp_core` 等是 MIT 或闭源），
> 以及 **MIT 部分（`warpui` / `warpui_core`）必须保留 Denver Technologies 的版权声明**。

<a id="s8-2"></a>
### 8.2 AGPL §5(a) 的"修改声明"怎么满足

> §5(a)：The work must carry **prominent notices stating that you modified it,
> and giving a relevant date.**（`LICENSE-AGPL:203-204`）

term4u 用三样东西共同满足，**不需要逐文件加头**：

| 手段 | 内容 |
|---|---|
| `README.md` 顶部的 fork 声明 | "term4u is a modified fork of Warp (`warpdotdev/warp`) at commit `066ec71…`, first modified on `<日期>`. See `LICENSES.md`." |
| `LICENSES.md` | 目录级映射 + 来源 commit |
| git 历史 | `upstream/master` 作为 base，每个改动 commit 都有日期。这是最"prominent"的修改记录 |

**"relevant date" 的落地**：README 里写一个明确的日期（第一次改动的日期），
不要只写"see git history"——git 历史可以被 rebase，README 的日期不会。

<a id="s8-3"></a>
### 8.3 §5(c)：整体许可

> §5(c)：You must license the entire work, as a whole, under this License.

这条**不影响 MIT 岛**——`warpui` / `warpui_core` 是可分离的、独立的作品
（separate works，§5 末段的 "aggregate" 例外），上游本身就是这么处理的。
term4u 只是延续上游的判断，不做新的判断。

> 但要注意：**如果 MIT 岛开始依赖更多 AGPL 代码，"可分离"这个前提会削弱。**
> 这正是 [§5](#s5) 的守卫要冻结现状的原因。

## 九、商标：不是许可证问题

<a id="s9-1"></a>
### 9.1 许可证不授商标权

| 许可证 | 条款 |
|---|---|
| AGPL-3.0 | §7(e)：`Declining to grant rights under trademark law for use of some trade names, trademarks, or service marks`（`LICENSE-AGPL:369-370`）——即许可证明确把商标权排除在外，且允许权利人附加此限制 |
| MIT | 全文只授予"use, copy, modify, merge, publish, distribute, sublicense, sell copies of **the Software**"。软件 ≠ 名称与标识 |

> **所以"我遵守了 AGPL"和"我可以叫 Warp"是两件毫不相干的事。** 前者是版权法，
> 后者是商标法。

<a id="s9-2"></a>
### 9.2 混淆可能性的三要素

商标侵权的核心判断是"混淆可能性"（likelihood of confusion）。三个最重的因素：

| 要素 | `warp4u` | `term4u` |
|---|---|---|
| **标识相似度** | 直接包含 `warp` 这个完整的商标词 | 不含任何上游商标词。`term` 是终端软件的**描述性通用词**，任何人都无法主张专有 |
| **商品/服务类别相同** | 完全相同（都是终端软件） | 完全相同 |
| **来源混淆的实际可能** | 高——同品类 + 含商标词 + **代码确实源自它**，用户完全可能以为是官方衍生版 | 低——名字上没有任何指向上游的成分 |

> `warp4u` 命中三要素中的两个最重的（相似度 + 同类），且第三个因素被"确实源自它"
> 这一事实**加重**而非减轻。这是商标混淆风险的典型形态，不是边缘案例。

<a id="s9-3"></a>
### 9.3 `term4u` 的实测数据

| 检查 | 结果 |
|---|---|
| crates.io | 未占用 |
| GitHub 同名仓库 | **0 个** |
| 对照组 `hearth` | 命中 6,979 个仓库，且前四全是《炉石传说》相关——已落选 |

<a id="s9-4"></a>
### 9.4 指称性合理使用（nominative fair use）

**可以做**（如实陈述事实，用于识别上游）：

- README 里写 `term4u is a fork of [Warp](https://github.com/warpdotdev/warp)`
- `LICENSES.md` 里写来源 commit
- commit message、issue、文档里提到 Warp
- 保留 `warp_*` crate 名与内部符号（[决策 D10](README.md#s2)）——这些是**内部标识符**，不是对外品牌

**不可以做**：

- 用 `Warp` 或含 `warp` 的名字作为**产品名**、二进制名、bundle id、URL scheme、
  应用显示名
- 使用 Warp 的 logo、图标、品牌配色
- 任何暗示官方关系的表述（"official"、"powered by Warp"、"Warp Edition"）

**三条判断规则**（源自指称性合理使用的经典要件）：

1. 只在**必要**时提及（识别上游需要提到它，产品命名不需要）；
2. 只用**必要的程度**（用文字 "Warp"，不用其 logo）；
3. 不暗示**赞助或背书**（显式声明 "not affiliated with, endorsed by, or sponsored by
   Denver Technologies, Inc."）。

## 十、贡献政策

term4u 目前是单人项目，但政策必须在第一个外部 PR 之前就位，否则事后无法补。

<a id="s10-1"></a>
### 10.1 DCO 而非 CLA

| 方案 | 选择 | 理由 |
|---|---|---|
| CLA（贡献者许可协议） | **不用** | CLA 的作用是让项目方获得再许可权（比如将来改成商业许可）。term4u 的 AGPL 部分**本来就没有再许可权**（版权在 Denver Technologies），CLA 拿不到任何有用的东西，只增加贡献门槛 |
| **DCO（Developer Certificate of Origin）** | **采用** | 只要求贡献者签署 `Signed-off-by:`，声明"我有权提交这段代码"。轻量、行业标准、法律效果明确 |

落地：`CONTRIBUTING.md` 里写明 DCO，并在 CI 里检查 `Signed-off-by:`。

<a id="s10-2"></a>
### 10.2 inbound = outbound

> **贡献进来的代码，许可证与它所在目录的许可证相同。**

| 贡献落在 | 许可证 |
|---|---|
| `app/`、`crates/*`（除 MIT 岛） | AGPL-3.0-only |
| `crates/warpui`、`crates/warpui_core` | MIT |
| `crates-local/*` | MIT |
| `docs/` | AGPL-3.0-only |

`CONTRIBUTING.md` 必须把这张表写出来，并明确：**向 MIT 岛提交代码 = 你的代码是 MIT**。

<a id="s10-3"></a>
### 10.3 两条硬规则

| # | 规则 | 检查方式 |
|---|---|---|
| C1 | **不得把 AGPL 代码复制进 MIT 目录** | `script/check_license_boundaries`（[§5](#s5)）+ 人工评审 |
| C2 | **不得引入新的网络出口** | 评审时检查是否新增 `http_client` / `websocket` / `reqwest` / `TcpStream` 的使用；守卫本身是默认拒绝，所以即使漏审也不会外发（H4） |
